# Фильтрация заявок и пользователей по бригаде

## Цель

Начальник бригады (`foreman`) видит только свою бригаду, её работников и заявки,
назначенные этим работникам. Глобальный диспетчер (`observer`) сохраняет полный доступ.
Исполнитель (`worker`) продолжает работать со своими назначенными заявками.

## Принятые решения

- `observer` остаётся глобальной ролью для диспетчерских операций.
- Добавляется роль `foreman`. Она не получает права создавать пользователей,
  назначать исполнителей или менять статусы заявок.
- Один работник имеет одну активную бригаду. Таблица участников сохраняется
  отдельной сущностью, чтобы позже добавить историю переходов без перестройки API.
- У бригады один начальник. Один `foreman` может руководить одной бригадой.
- Заявка попадает в выборку начальника, если в `ticket_assignments` есть хотя бы
  один работник его бригады. Неназначенные заявки начальник не видит.
- Поле `brigade_id` в запросе остаётся фильтром, а границей доступа служит
  `current_user.id` и серверная проверка роли.
- Существующие анонимные чтения заявок сохраняются, чтобы не менять внешний
  контракт этой итерации. При авторизованном `foreman` запросы получают ограничение.

## Сущности

### `brigades`

- `id` — целочисленный первичный ключ;
- `name` — уникальное имя без пробелов по краям;
- `foreman_id` — внешний ключ на `users.id`, роль пользователя проверяет сервис;
- `created_at`, `updated_at`.

Уникальные индексы запрещают повторять имя бригады и назначать одного начальника
двум бригадам.

### `brigade_members`

- `brigade_id` — внешний ключ на `brigades.id`;
- `worker_id` — внешний ключ на `workers.user_id`;
- составной первичный ключ `(brigade_id, worker_id)`;
- уникальный индекс на `worker_id`, поэтому работник входит только в одну активную бригаду.

Удаление работника каскадно убирает его членство. Удаление начальника, который
руководит бригадой, сервис блокирует до переназначения.

## API

- `POST /api/v1/brigades` — `observer` создаёт бригаду, назначает `foreman_id`
  и список `worker_ids`.
- `GET /api/v1/brigades` — `observer` получает все бригады, `foreman` свою,
  `worker` бригаду с собственным участием.
- `GET /api/v1/brigades/{id}` — тот же контроль видимости для одной бригады.
- `PUT /api/v1/brigades/{id}/members` — `observer` заменяет начальника и полный
  список работников атомарно.
- `GET /api/v1/users?brigade_id=...` — фильтр для `observer`; для `foreman`
  результат пересекается с его бригадой и включает самого начальника.
- `GET /api/v1/tickets?brigade_id=...` — заявки с назначенными работниками бригады;
  для `foreman` условие дополнительно ограничивается его `current_user.id`.

Детальный просмотр заявки и профиля пользователя применяет тот же контроль,
чтобы ID в URL не обходил ограничение списка. Комментарии заявки используют
ту же проверку для чтения и записи: `foreman` создаёт комментарии для заявок
своей бригады и редактирует только собственные комментарии.

## Данные и импорт

Предоставленные CSV не содержат стабильного ID работника или начальника, поэтому
автоматический импорт состава в эту итерацию не добавляется. Бригады создаются
через API после появления источника с `foreman_id` и `worker_ids`.

## Тестирование

- миграция создаёт таблицы, индексы и ограничения;
- `observer` создаёт бригаду и меняет её состав;
- нельзя назначить не-`foreman` начальником, неизвестного работника или работника
  из другой бригады;
- `foreman` видит только своих работников и заявки своей бригады;
- чужая заявка возвращает 404 в детальном API и не попадает в список;
- `foreman` создаёт комментарии по доступным заявкам и редактирует только собственные;
- `observer` сохраняет полный доступ;
- смена роли или удаление пользователя не оставляет неконсистентное членство;
- прежние фильтры заявок и пользователей продолжают работать.
