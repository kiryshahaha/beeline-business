# Backend и планировщик: сверка с каждым вопросом и ответом, аудит и план доработок

Проверка начата 21.09.2026, документ завершён 22.09.2026 по МСК; дата в имени файла обозначает начало аудита. Проверенная версия: **`main`, `e789d9b27c46c006dd8cc4af3901c3979f0e7d6d`**. В начале проверки рабочее дерево было чистым. Это новый аудит текущей версии, включая расписание, три раздела аналитики, отчёты и календарь из последних PR. Выводы старого аудита от 18.09 не считаются доказательствами для этой версии.

**Главный вывод:** backend уже связан с единственным планировщиком и Geoapify. Есть существенная техническая основа: подготовка ограничений, матрицы для разных видов транспорта, проверка ответа решателя, preview/apply, транзакционное сохранение назначений и GeoJSON. Однако бизнес-модель пока не соответствует нескольким центральным ответам экспертов: окно начала работ трактуется как окно завершения, нет приоритетов типов заявок, обязательного сокращения числа исполнителей, изоляции участков и стартов из дома. Текущий алгоритм предназначен для первичного распределения перед началом смены, а не для изменения уже выполняемого дня. Новые модули отображают данные, но не закрывают эти пробелы.

В ходе аудита производственная логика, миграции, README и рабочая БД не изменялись. Результат работы — этот документ. Диагностические записи выполнялись только в отдельных автоматически очищаемых схемах тестовой БД. Исправления ниже — **предлагаемые работы**, а не выполненные изменения.

## 1. Как читать документ и откуда взяты требования

Цепочка проверки: **вопрос/ответ M, C или P → доказательство E → проблема F → задача T → приёмка A**. Таблицы M и C идут в порядке источников: повторные вопросы сохранены отдельно, а противоречивые ответы не объединены молча.

Статусы:

- **Есть** — соответствующее поведение присутствует в коде; это само по себе не означает успешный полный E2E.
- **Частично** — основа есть, но существенная часть условия не выполняется.
- **Расхождение** — код выполняет другое правило.
- **Нет** — соответствующая модель или операция не найдена.
- **Не проверено** — необходимое выполнение или исходный материал недоступны.
- **Опция / вне реализации** — эксперт не требует эту возможность либо речь об организации мероприятия.

Приоритеты работ: **P0** — мешает корректному плану, безопасной работе с данными или воспроизводимому запуску; **P1** — требуется для законченного решения и его демонстрации; **P2** — улучшение после закрытия основного сценария. Это приоритеты проекта, а не приоритеты клиентских заявок.

## 2. Как система работает сейчас

1. Backend хранит адреса, пользователей, исполнителей, навыки, бригады, офисы, заявки, назначения, складские остатки, резервы, уведомления и маршруты в PostgreSQL.
2. Диспетчер (`observer`) отправляет `route_date`, конкретные `ticket_ids`, `worker_ids` и `allow_partial` в `POST /api/v1/planning/preview`.
3. Backend читает согласованный снимок БД. Проверяет статус заявки, наличие назначения, координат, настроенного вида работ, навыков и резервов. Исполнитель со сменой, которая уже началась, исключается. Занятый исполнитель также исключается целиком.
4. Backend собирает координаты и запрашивает у **Geoapify Route Matrix** ориентированные матрицы времени/расстояний по профилям транспорта. Одинаковые координаты переиспользуются, заявки при этом остаются отдельными задачами.
5. Единственный planner получает подготовленную задачу через **`POST /api/v1/solve`**. OR-Tools выбирает исполнителей и последовательности. У него нет собственной БД и нет самостоятельной бизнес-логики BK/HD, склада или статусов.
6. Backend независимо проверяет решение. Затем запрашивает у **Geoapify Routing** геометрию выбранных переездов и проверяет согласованность времени и линий.
7. Preview хранится с входным снимком, fingerprint и сроком действия. Он ещё не изменяет назначения.
8. `apply` под блокировками проверяет актуальность снимка и атомарно сохраняет маршруты, назначения, плановые времена и события уведомлений. Повторное применение возвращает прежний результат.
9. Расписание читает текущие назначения и плановые интервалы. Аналитика считает состояния заявок, нагрузку бригад и последние изменения. Отчёты выгружают заявки. Календарь выдаёт личную ICS-подписку исполнителя.

Таким образом, **Geoapify строит матрицы и дорожные линии, OR-Tools распределяет задачи, backend управляет бизнес-данными и сохранением результата**. Связь backend ↔ planner уже реализована. Создавать второй planner или новый параллельный `/v2/solve` для доработок не требуется.

### 6.5. Что стоит сохранить

Не требуется переписывать весь backend. Сохранить согласованный snapshot, короткие транзакции без сетевых вызовов внутри, fingerprint/TTL, атомарный apply и повторную квитанцию, отдельную проверку solver-response, строго типизированные DTO, маркировку приближённого транспорта, различие logical visit и unique coordinate, нумерацию маршрутов под блокировкой, изолированные миграционные тесты, ограниченный импорт и безопасный обмен данных. Доработки должны расширять эти гарантии. Например, изменение objective без изменения `validate_solution` сломает ответы; изменение модели маршрута без updates CSV/XLSX/Bruno/ICS оставит систему внутренне несогласованной.

## 7. Полный план реализации с зависимостями и результатами

### T01. Зафиксировать исполняемые правила кейса — P0

**Основание:** M17/M19/M44, C19/C32/C38/C41/C42, P03/P05. **Зависимостей нет.**

1. Описать одну `planning_policy`: окно начала, service duration, приоритеты, предел смены/SLA, открытый маршрут, замороженные состояния, правило территории и допустимые ручные действия.
2. Разделить подтверждённые правила и решения команды. Иерархия авария/подключение/остальные подтверждена; точные численные обмены между ASAP и количеством работ — выбор политики.
3. Предлагаемый стартовый порядок целей: сохранить hard constraints; минимизировать неназначенные аварии; минимизировать задержку реакции на них; минимизировать неназначенные подключения; минимизировать все неназначенные; затем активных работников; затем время пути; при равенстве уменьшать ненужные изменения прежнего плана. Это **предложение для реализации**, не дословная математическая функция экспертов. Оно сознательно допускает потерю обычных визитов ради более ранней аварии; этот trade-off показать отдельным тестом и метриками.
4. `policy_version` и параметры сохранять со снимком; никогда не пересчитывать историю по сегодняшним настройкам.

**Готовность:** правила изложены кратко и однозначно, каждому соответствует тест A01–A18; никакого автоматического сдвига обещаний клиента. План работ остаётся здесь, в README модулей описывается только реализованное поведение.

### T04. Исправить время, ожидание и открытые маршруты — P0

Названия ниже — предлагаемый контракт первой реализации, а не утверждение о существующих таблицах. Его можно адаптировать к стилю проекта, сохраняя перечисленные инварианты.

Для количества оборудования принять простое явное правило: требование типа работ — минимальный обязательный комплект; ticket-specific quantity того же appliance — полный уточнённый объём заявки, поэтому эффективное количество = `max(type_minimum, ticket_quantity)`, а разные appliance суммируются независимо. Если конкретный бизнес-кейс требует аддитивных позиций, хранить такие позиции отдельно с явным назначением. Это решение команды, его нужно закрепить тестом, чтобы не удвоить один роутер при объединении требований.

Миграция не должна терять существующие маршруты/заявки. Перед добавлением NOT NULL/FK: собрать unmapped work_type и неразрешённые service_area, показать отчёт, выполнить backfill по утверждённой таблице, затем включить constraints. Существующие строковые work_type можно оставить как исторический raw label. Не присваивать всем неизвестным данным один случайный участок или первый тип работ.

### 7.3. Предлагаемые операции API и граница solver

| Операция | Поведение |
| --- | --- |
| `POST /api/v1/planning/preview` | Оставить существующую точку входа; расширить контекстом service_area/date, initial/replan, as_of, base_revision. Backend сам выбирает область заявок/смен; если переданы ID, проверяет их scope. Матрицы и разрешённые исполнители по-прежнему не принимаются от браузера как доверенные данные. |
| `POST /api/v1/planning/plans/{plan_id}/apply` | Существующий apply, дополненный CAS по base/current revision и ресурсом. Ответ содержит revision, route IDs/ordinals, metrics и квитанцию повторного выполнения. |
| `GET /api/v1/planning/day-plans` и `GET .../{id}/revisions` | Найти план участка/дня, текущую ревизию и историю; перестать требовать от пользователя помнить UUID preview. |
| `GET /api/v1/planning/plans/{plan_id}/diff` | Сравнить с base_revision: worker, порядок, ETA/start/end, добавление/снятие, причины и метрики. |
| `POST /api/v1/tickets/{id}/events` | Записать execution/cancellation/progress event с occurred_at, actor, reason и idempotency key; не принимать произвольные противоречащие переходы. |
| `POST /api/v1/workers/{id}/availability-events` | Зафиксировать интервал недоступности и причину; инициировать или предложить replan затронутого дня. |
| `POST /api/v1/planning/plans/{plan_id}/manual-preview` | Проверить назначение/порядок/pin/согласованное окно теми же hard constraints, вернуть новую предложенную ревизию и diff. Запись только через apply. |
| `POST /api/v1/inventory/issue` / `return` | Зафиксировать физическое движение; расход по ticket-completed проходит через общий idempotent ledger. |
| `POST /api/v1/data/import` с явным import profile | Сохранить domain exchange; добавить case-specific adapter и preview отчёта. Raw source и normalized DB package — разные форматы. |

Solver продолжает получать **численную задачу**: логические nodes/visits, профильные матрицы, service durations, окна начала, starts/ends, доступность vehicles, allowed vehicles и objective parameters. Он не читает tickets из БД и не изменяет склад. Backend готовит эту задачу из проверенного состояния, затем независимо проверяет результат. Изменение wire contract выполняется одновременно в backend/planner и их тестах; само по себе повышение версии payload при несовместимом изменении не означает создание второго планировщика.

Минимальный публичный результат дополнить полями `metrics` (assigned/unassigned by category, active_workers, distance/travel/service/wait), `objective` (policy/version/breakdown), `rejections` (code/message/details), `base_revision_id`/`revision_id` и однозначными временами stop. Сейчас эти поля в таком виде **не реализованы**. Секреты, полные входные снимки и сырые матрицы остаются внутренними.
