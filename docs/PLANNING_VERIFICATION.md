# Проверка интеграции существующего планировщика

Дата проверки: 20 сентября 2026 года. Изменения относятся к одному planner с
`POST /api/v1/solve` и `contract_version=1`. Второго сервиса или `/api/v2/solve` нет.

Реализация подготовлена, но полная приёмка **не завершена**: в локальном окружении
не установлены OR-Tools и Firebase Admin, а загрузка зависимостей и доступ к GitHub
завершались сетевыми ошибками. Зелёный GitHub Actions и запуск реального оптимизатора
этим отчётом не подтверждаются.

## Реализованное поведение

Backend получает согласованный снимок данных, проверяет смены, транспорт, окна,
навыки и оборудование, запрашивает матрицы Geoapify и передаёт задачу существующему
решателю. Цель — сначала максимальное число выполненных заявок, затем минимальное
суммарное время поездок. Обслуживание учитывается в смене; фиксированной платы за
использование инженера нет. Ограниченный по времени поиск не гарантирует глобальный оптимум.

Ответ решателя независимо проверяется backend. Для выбранных переходов запрашивается
дорожная геометрия, после чего сохраняется предложение с ограниченным сроком действия.
`apply` проверяет актуальность снимка и атомарно сохраняет назначения, плановые времена,
GeoJSON, номера маршрутов и события уведомлений. Повторное применение не создаёт дубликаты.

Контракт, файлы и ограничения описаны в [README модуля планирования](../backend/app/modules/planning/README.md).
В частности, поддерживается планирование неназначенных заявок до начала смены.
Перестроение уже начавшегося дня и подключение нового процесса к интерфейсу карты
в эту реализацию не входят.

| Отдельные новые проверки планирования | 23 успешно; настоящая PostgreSQL, тестовые ответы решателя и Geoapify |
| Ruff и форматирование | Успешно для backend и planner, 217 Python-файлов |
| Миграции | Upgrade, downgrade, повторный upgrade и Alembic check в отдельных схемах PostgreSQL проходят |
| Обязательность PostgreSQL | Без TEST_DATABASE_URL — ошибка; при недоступном сервере — ошибка соединения и ненулевой код, без skip |
| Контракт backend ↔ planner | Файлы моделей идентичны; невалидные ответы, расписания и метрики отклоняются тестами backend |
| Bruno через HTTP | 133/133 запроса, 131/131 тест, 173/173 assertion на локальном диагностическом стенде **с тестовым решателем** |
| Синтетические данные | 6 сценариев планирования проходят оба парсера, реальные ограничения БД и проверку расписания backend с тестовым решателем |
| Контроль файлов данных | SHA-256 совпадает для всех 12 файлов планирования и 4 общих CSV ZIP/XLSX |
| Конфигурация | YAML workflow разбирается; `docker compose --env-file .env.docker.example config --quiet` проходит |
| Реальный OR-Tools | Не выполнено: отсутствует пакет `ortools`; тесты и обязательный E2E завершаются ошибкой, не пропускаются |
| GitHub Actions | Workflow обновлён; удалённый запуск и его результат не подтверждены |
| Реальный Geoapify | В этой проверке использован детерминированный тестовый HTTP-провайдер; доступность и данные внешнего сервиса не подтверждены |
| Docker и frontend | Полный запуск Compose из чистого checkout, lint/build frontend в этой сессии не подтверждены |

Проверенные случаи включают параллельное и повторное применение, конфликт двух планов,
устаревший снимок, истечение срока, атомарный откат, авторизацию, отказ провайдера,
поддельный ответ решателя, одинаковые координаты, ночные смены, перегрузку,
разные виды транспорта и разрывы дорожной MultiLineString.

HTTP-прогон с тестовым решателем проверяет взаимодействие процессов и API, но **не
доказывает работоспособность OR-Tools или качество оптимизации**. Подмена использовалась
только в локальном диагностическом сценарии в игнорируемой `.local`. Версионируемый
`run_planning_e2e.py` запускает настоящий planner; обход отсутствующего OR-Tools в CI не добавлен.

Общие наборы содержат 25 предметных таблиц:

|---|---:|---:|
| `data/synthetic/standard` | 1 500 | 7 984 |

В [data/planning](../data/planning/README.md) дополнительно находятся mixed,
duplicate_coordinates, night, rejections, overload, volume — каждый в CSV ZIP и XLSX.
Сценарии используют фиксированную дату 2030-01-15 и явно указанные тестовые часы.
В реальном приложении обычные проверки текущей даты не отключаются.

Проверки выполнены на Windows, Python 3.12.5, PostgreSQL 17, Node.js 22.23.2,
Bruno CLI 4.1.0. По сверке установленных пакетов с requirements отсутствуют только
`firebase-admin` и `ortools`. OR-Tools закреплён на 9.15.6755.
HTTPS-загрузка пакетов завершалась тайм-аутами, обращение к GitHub — сбросом соединения.

Локальные логи сохранены в игнорируемой папке `.local` корня проекта:

- `planning-backend-final.log` — полный прогон 227 тестов;
- `planning-feature-final.log` — отдельные 23 проверки;
- `planning-required-db.log`, `planning-unreachable-db.log` — обязательность БД;
- `planning-solver-tests.log`, `planning-e2e-attempt.log` — ошибки запуска настоящего planner;
- `planning-transport-only.log`, `planning-transport-only/bruno.xml` — HTTP-диагностика с тестовым решателем.

## Воспроизведение обязательных проверок

Нужны доступ к пакетным реестрам, Node.js и **отдельная** PostgreSQL-БД с именем,
оканчивающимся на `_test`. Ниже `beeline_test` — пример такой уже созданной БД;
указать свои тестовые реквизиты. Команды PowerShell из корня репозитория:

```powershell
Set-Location backend
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install --only-binary=ortools --require-hashes -r requirements.lock -r ..\planner\requirements.lock
.\.venv\Scripts\python.exe -m pip check

$env:TEST_DATABASE_URL = 'postgresql+psycopg://beeline_test:beeline_test@127.0.0.1:5432/beeline_test'
$env:DATABASE_URL = $env:TEST_DATABASE_URL
$env:JWT_SECRET_KEY = 'isolated-local-test-secret-at-least-thirty-two-characters'
$env:NOTIFICATION_DISPATCHER_ENABLED = 'false'
$env:PYTHONUTF8 = '1'

.\.venv\Scripts\python.exe -m ruff check . ..\planner
.\.venv\Scripts\python.exe -m ruff format --check . ..\planner
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe generate_planning_synthetic.py --output .local/planning-synthetic
.\.venv\Scripts\python.exe run_planning_e2e.py --report-dir .local/planning-e2e

Set-Location ..\planner
..\backend\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Проверять код завершения каждой команды: PowerShell сам не останавливает всю последовательность
после ошибки нативного процесса. E2E создаёт и удаляет свою схему БД и свои процессы,
использует настоящее HTTP-взаимодействие с OR-Tools и тестовый Geoapify без внешних ключей.
Первый запуск Bruno через `npx` требует загрузки CLI; можно передать путь к уже
установленному CLI через `--bruno-command`.

В [GitHub Actions](../.github/workflows/backend-tests.yml) обязательны полный backend,
полный набор native-тестов planner и E2E с настоящим решателем. Успех диагностического
прогона с подменой не является основанием считать эти проверки пройденными.
