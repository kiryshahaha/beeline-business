# Политика планирования: контракт кейса и правила сохранённого расчёта

T01 вводит проверяемый контракт правил и сохраняет параметры действующего расчёта.
Существующий `/api/v1/solve` остаётся единственным solver. Этот документ объясняет
реализованный механизм версионирования, а не объявляет все требования кейса выполненными.

## Два явно различимых представления

`GET /api/v1/planning/policy` доступен наблюдателю и возвращает:

- `execution`: действующую политику и лимит поиска из конфигурации сервиса;
- `case_contract`: нормативный контракт `beeline_case`, версия 1,
  с `activation: "contract_only"`. Его нельзя включить передачей параметров в preview.

Действующая политика — версия 2: solver исполняет порядок целей контракта (см.
[исполняемую цель](#исполняемая-цель-solver-t05)). Остальные поля описывают только
реализованные ограничения; поле версии не служит доказательством соответствия всему
кейсу.

Полный контракт с происхождением каждого правила, M/C/P/U-ссылками, A-критериями
и соответствующими задачами хранится в
[`case_policy_v1.json`](../backend/app/modules/planning/case_policy_v1.json).
`confirmed` означает подтверждённое требование, `team_decision` — выбранное в T01
допущение. Ранний ответ M17 о приоритетах заменён последними C32/C40.

## Принятая иерархия целей контракта

Сначала обязательны жёсткие ограничения. Допустимые кандидаты для одного набора
заявок, момента расчёта и неизменяемого префикса сравниваются лексикографически:

1. Число неназначенных аварий.
2. Сумма минут реакции на обслуженные аварии.
3. Число неназначенных подключений.
4. Общее число неназначенных заявок.
5. Число использованных инженеров — без пустых маршрутов.
6. Минуты пути.
7. Число изменённых будущих визитов.

Реакция — время от `received_at` до начала обслуживания, округлённое вверх до минут.
Repair и additional равноправны. Изменение визита — другой инженер, начало либо
относительный порядок среди сохранившихся визитов; один визит считается один раз.
Полное равенство ключей не предписывает выбор конкретного инженера.

Это решение команды, а не численные веса из ответа эксперта. Оно сознательно
выбирает начало аварии в 12:05 с четырьмя неназначенными обычными визитами вместо
начала в 12:06 с выполнением всех обычных. При равном числе обслуженных аварий
суммарная реакция может влиять и на выбор их поднабора. Эти последствия явно
показаны в [11 синтетических сравнениях](../data/planning/policy_objective_cases.json).

`case_policy.objective_key` исполняет **эталонное сравнение уже рассчитанных метрик**,
отклоняет кандидаты с hard violations и некорректными счётчиками. Он не строит
маршруты и не заменяет OR-Tools.

## Исполняемая цель solver (T05)

`ExecutionPolicy` версии 2 передаёт этот порядок в единственный `/api/v1/solve`:
`unassigned_emergencies`, `emergency_response_minutes`, `unassigned_connections`,
`unassigned_total`, `active_workers`, `travel_minutes`, `reassigned_visits`.
Первые шесть уровней совпадают с контрактом. Седьмой уже `changed_future_visits`:
solver считает только визиты, переданные другому инженеру относительно текущего
назначения. Изменение времени или порядка у того же инженера целевая функция не
штрафует, его показывает `replan_diff` предпросмотра перепланирования.

Техническая реализация — одна взвешенная сумма с доказанными границами. Для задачи
вычисляется наибольшее значение каждого уровня: число аварий, подключений и заявок,
сумма `min(конец окна, SLA − обслуживание) − received_at` по авариям, число
инженеров, сумма длин их смен (путь маршрута не длиннее смены) и число визитов с
текущим исполнителем. Вес уровня на единицу больше наибольшей суммы всех младших
уровней, поэтому одна единица старшего уровня перевешивает любые изменения младших.
Итог ограничен 2^62, чтобы OR-Tools не выходил за int64 во время поиска; иначе preview
отклоняется с `planning_limit_exceeded`. При лимитах backend (100 заявок, 20 инженеров)
это достижимо только при искусственно широких окнах и давних авариях.

- Авария: штраф пропуска и мягкая верхняя граница времени начала в момент
  `received_at`. Широкое окно не разрешает откладывать аварию ради пути.
- Инженер: фиксированная стоимость OR-Tools, начисляется только непустому маршруту.
- Путь: минуты поездок без обслуживания. Переназначение: надбавка на дугу в визит,
  если инженер отличается от текущего.

Planner возвращает `objective_components`, `objective_weights` и `total_cost` и сам
сверяет итог OR-Tools с разложением. Backend независимо пересчитывает разложение по
проверенным маршрутам, веса по задаче и итог; любое расхождение —
`502 planner_invalid_response`. Preview отдаёт `objective_components`, ревизия дня
хранит их вместе с `planning_policy`; у ручной правки ревизии они `null`.

Поиск эвристический (GUIDED_LOCAL_SEARCH с лимитом времени): FEASIBLE означает лучший
найденный план, не доказанный оптимум. Малые задачи в `planner/tests/test_objective.py`
сверяются с полным перебором по тому же ключу.

## Остальные зафиксированные решения

Контракт охватывает A01–A18: полное выполнение работы в клиентском окне включительно, ожидание отдельно от ETA,
сервис без нормативной дороги, конец смены и отдельный аварийный SLA, открытый
маршрут, домашний старт отдельно от склада, участок, навыки и транспорт, оборудование
на руках и недопустимость повторного расхода. Начатая работа и выполненные визиты
заморожены; по умолчанию текущий переход тоже сохраняется до подтверждённого
перенаправления. Новые события любых категорий пересчитывают только допустимый
остаток, с подтверждением диспетчера. Клиентское окно автоматически не меняется.

Проверка структуры и трассировки контракта **не закрывает** бизнес-приёмку A01–A18.
Реализация ограничений и интеграционные сценарии относятся к T02–T08/T17.
Reference-тесты показывают выбор политики по A09–A12 на готовых метриках, а
`planner/tests/test_objective.py` проверяет те же компромиссы на настоящем OR-Tools.

## История и применение

Новый preview сохраняет полную `planning_policy` в `planning_plans.input_snapshot`
и возвращает её публично. В ней есть версия, параметры текущих ограничений,
цель, правило штрафов и фактический лимит поиска. Параметры входят в fingerprint;
конкретные нормы работ и требования остаются в том же исходном снимке БД.
`problem.policy_version` передаётся в существующий `/api/v1/solve`; неизвестная
версия отвергается строгим контрактом обеих сторон.

Чтение истории и проверка актуальности используют сохранённые параметры.
Изменение сегодняшнего лимита поиска не переписывает историю и не делает
выполнимый сохранённый preview устаревшим. Apply проверяет совместимость сохранённой
политики до записи маршрутов; неподдерживаемая/неполная политика — `409
planning_policy_unsupported`. Повтор уже выполненного apply возвращает прежнюю
квитанцию, даже после истечения TTL. Атомарность, блокировки и idempotency сохранены.

У планов до T01 полный набор параметров отсутствует. API возвращает
`planning_policy: null`, не подставляя текущие настройки и не изменяя JSONB.
Новые preview записывают версию 2 с параметром `visit_window=whole_service`: конец работы
не позже конца клиентского окна. Старые снимки версии 2 с параметром
`service_start_in_window` сохраняют записанный смысл при чтении истории. Снимки прежней версии 1 (цель «больше заявок,
затем путь») по-прежнему читаются и применяются; их исходные fingerprint не меняются,
но заново через solver они не рассчитываются. Неизвестная версия до записи отклоняется.

Новая миграция и изменение CSV/XLSX не нужны: используется существующий JSONB;
в обмене предметными таблицами `planning_plans` не экспортировались и не экспортируются.
Данные маршрутов и потребители schedule/calendar не меняют формат.

## Проверка

Из `backend` с установленными обоими requirements:

```powershell
python -m unittest tests.test_planning_policy -v
python -m unittest tests.test_planning_api -v
python verify_synthetic.py
python run_planning_e2e.py --report-dir .local/planning-e2e
```

DB-тесты и E2E требуют `TEST_DATABASE_URL` на отдельную PostgreSQL БД `*_test`;
её отсутствие — ошибка, не skip. `test_planning_api` использует fixture planner
для транзакций. `run_planning_e2e.py` запускает настоящий backend и OR-Tools через
HTTP, PostgreSQL и Bruno; только Geoapify заменён детерминированным сервером.
Проверка пакетов сверяет SHA-256, строки и семантическое равенство обоих форматов,
а также совпадение Bruno planning fixture с исходным набором.
