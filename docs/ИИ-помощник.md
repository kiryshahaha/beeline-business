# ИИ-помощник в Beeline Business

## Зачем он нужен

Новая система меняет ежедневные привычки сразу у нескольких ролей. Инженеру нужно понимать, где посмотреть следующий адрес, почему изменилось назначение, что взять на заявку и как выполнить действия в приложении. Чат-помощник встроен в рабочий интерфейс инженера, чтобы подсказывать по его смене и помогать осваивать процедуры без поиска по разрозненным документам.

Это прикладная функция адаптации команды к новому процессу. Помощник не заменяет обучение, руководителя или регламент и не принимает за диспетчера решений по маршруту.

## Что может спросить инженер

В мобильном интерфейсе доступны быстрые вопросы и свободный ввод. Типичные темы: следующая заявка, время завтрашней смены, причина переноса, оборудование по работе и инструкция к типовой операции. Если чат открыт из конкретной заявки, запрос может получить контекст этой заявки.

## Два источника ответа

### Факты из системы

Основной backend после проверки доступа передаёт сведения, необходимые для ответа: день и смену инженера, плановые заявки, а для связанной заявки — разрешённые детали, комментарии, оборудование и историю. Для распознанных фактических вопросов текст собирает модуль фактов, а не языковая модель. Интерфейс помечает такой ответ источником «данные системы».

### Инструкции для роли

Для вопроса «как сделать» сервис ищет подходящие разделы внутренней Markdown-базы знаний с учётом роли и, если возможно, категории работы. Языковая модель формулирует ответ на основе найденных инструкций. Интерфейс показывает тип источника, а при использовании базы знаний может показать связанные материалы.

Генеративный ответ может ошибаться. Для вопросов безопасности и нормативных действий нужно следовать утверждённому регламенту; чат не является источником обязательного решения.

## Как это помогает внедрению

- Инженер спрашивает о своём следующем шаге, не переходя в диспетчерскую панель.
- Вопрос можно задавать словами, которыми сотрудник пользуется в работе.
- Объяснение опирается на доступный именно этой роли контекст, а не на чужие данные.
- Ролевые инструкции находятся рядом с ежедневными заявками и оборудованием.
- Ответы по данным отделены от сгенерированных разъяснений, что помогает пользователю оценивать источник.

Эти преимущества описывают назначение и устройство функции. Сокращение времени обучения или числа обращений к диспетчеру нужно измерить в пилоте и не считать заранее достигнутым эффектом.

## Роли и границы доступа

Пользовательскую сессию проверяет backend. Он определяет роль, собирает доступный контекст и вызывает внутренний Assistant API. Сам Assistant не подключается к PostgreSQL и не авторизует пользователя самостоятельно. В backend реализованы роли worker, foreman и observer; экран чата включён в рабочее приложение инженера.

Помощник не назначает исполнителей, не изменяет маршрут, не подтверждает выполнение заявки и не записывает данные. Для этих действий используются отдельные операции приложения.

## Архитектура

    Экран инженера
         │ вопрос
         ▼
    Backend: проверка роли и контекста
         │
         ▼
    Assistant API
      ├─ разбор фактов из переданного контекста
      └─ поиск ролевой инструкции → Ollama → текст ответа

Assistant stateless: контекст и история передаются вместе с запросом; сервис не хранит историю переписки между вызовами. Backend ограничивает частоту обращений и журналирует результат.

## Модель и эксплуатация

В стандартной конфигурации используется Ollama и модель из параметра ASSISTANT_MODEL; шаблон указывает qwen3.5:2b. Отдельно подготовлен процесс обучения LoRA и сборки модели Beeline в GGUF, но файл модели не включён в репозиторий и должен быть установлен отдельно. Наличие обучающего процесса не означает, что специализированная модель загружена в текущей среде.

Чат требует включённого Assistant-сервиса. Ответы по фактам могут формироваться без генеративной модели, если Assistant работает; ответы по инструкциям требуют доступной модели. Если сервис или модель недоступны, пользователь должен получить сообщение о недоступности, а не выдуманный результат.

## Данные и приватность

Основной backend определяет, какие сведения разрешено передавать. Assistant API stateless, однако конфиденциальность также зависит от журналов, сетевой конфигурации и размещения Ollama. Локальная модель сама по себе не доказывает отсутствие хранения данных. Для персональных и клиентских сведений используйте только одобренную конфигурацию проекта.

## Как оценивать функцию на пилоте

С согласия команды можно измерить время ответа на типовые вопросы, долю ответов со ссылкой на нужный раздел инструкции, число повторных обращений к диспетчеру по теме интерфейса и оценку полезности со стороны инженеров. Отдельно нужно проверять точность фактических ответов и отсутствие неподтверждённых инструкций.
