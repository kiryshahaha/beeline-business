# Расчёт VRPTW

| Файл | Назначение |
| --- | --- |
| `schemas.py` | SolveRequest: матрицы, окна, длительности, допуски и параметры; SolveResponse/Route/Step |
| `service.py` | OR-Tools RoutingModel, временная размерность, штрафы, допуски машин, извлечение решения |
| `router.py` | POST /api/v1/solve, запуск вычисления и ответ |

Сервис не читает PostgreSQL и не знает ID работников, адресов и заявок backend.
`vehicle_id` — индекс во входном массиве, `node` — индекс точки. Время, длительность
и time_matrix должны быть в одинаковых единицах (в проекте — минуты).
arrival_time — абсолютная координата времени в этой шкале, например 540 = 09:00,
а не длительность после предыдущей точки. Единицы distance_matrix задаёт вызывающий.

Алгоритм строит начальное решение PATH_CHEAPEST_ARC, затем улучшает его с
GUIDED_LOCAL_SEARCH до лимита времени. Стоимость — переезды плюс обслуживание,
фиксированная стоимость использованной машины и штрафы за пропущенные точки.
allowed_vehicles ограничивает назначения; квалификация/транспорт должны заранее
быть преобразованы вызывающим кодом в этот список. Метрики расстояния складываются
из distance_matrix, если она передана.

Чтобы сохранить результат, вызывающий код сопоставляет индексы реальным ID,
переводит arrival_time в ISO timestamp с датой/часовым поясом и отправляет
упорядоченные stops в POST backend /api/v1/routes/batch. Автоматического адаптера
между сервисами пока нет. Оба каталога называются app: запускайте сервисы
из разных рабочих директорий, не смешивая их в одном PYTHONPATH.

Ограничения валидации и точности статуса OPTIMAL отражены в аудите. Нахождение
эвристического решения за лимит времени само по себе не доказывает оптимум.
