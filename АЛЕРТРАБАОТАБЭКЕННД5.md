# План 5: финальная проверка планов 1–4 на синтетических данных

> Этот документ — сценарий итоговой приёмки. Запускать его после выполнения всех задач планов 1–4. Наличие этого файла или тестовых фикстур не означает, что проверки уже запускались или прошли.

## Цель и условия начала

Проверить систему сквозным путём: загрузка данных → однодневный roster → первоначальный план → события в течение дня → обычная безопасная вставка или аварийный replan → GeoJSON/ревизии/уведомления → API/Bruno/CI. Проверки должны использовать синтетические данные, но настоящий backend, PostgreSQL и native planner. Геосервис можно заменять воспроизводимой дорожной матрицей/Geoapify stub только там, где отдельно проверяется контракт интеграции; такой stub не считается native planner E2E.

Начинать прогон только при выполнении всех условий:

- T-задачи планов 1–4 закрыты по их критериям, миграции применимы с нуля;
- рабочая ветка и HEAD записаны, diff чистый или все локальные изменения перечислены;
- зависимости, версии окружения и команды запуска зафиксированы в README/lock-файлах;
- PostgreSQL тестового окружения доступна; обязательные DB-тесты при недоступности завершаются ошибкой, без `skip`;
- установлен и запускается настоящий solver, обязательная интеграция не заменена fixture-планировщиком;
- определены внешние секреты/ключи Geoapify в CI secrets, а локальные секреты не попадают в synthetic dataset;
- временная зона и дата тестового дня фиксированы, генератор данных имеет seed.

## Пакет синтетических данных

Создать версионируемый набор под текущей структурой проекта (предлагаемое размещение: `data/synthetic/acceptance/`; если в проекте уже есть официальный каталог fixtures, использовать его и сослаться здесь). Сохранить генератор, seed, схему, manifest и краткое описание ожидаемых исходов. Данные должны быть псевдореальными, без персональных данных.

Минимальный объём: 3 региона/участка, 2 городских/удалённых зоны внутри каждого региона, 12 работников в дневном roster (разные навыки, транспорт и оборудование), 36 плановых обычных заявок, 12 новых заявок в течение дня, из них 6 аварий и 6 обычных; набор должен иметь варианты полностью допустимых, пограничных и заведомо невыполнимых сценариев. Дополнительно — отдельные компактные fixtures для точечных тестов и конфликтов.

В manifest записать seed, версии схемы/генератора, временную зону, дату, число строк по таблицам, контрольные суммы файлов, известные ожидаемые назначения и происхождение каждой синтетической дорожной матрицы. CSV и XLSX должны представлять одни и те же логические данные; импорт обоих форматов обязан давать эквивалентный нормализованный результат.

Состав пакета:

- workers: участок, бригада, профиль дневной смены 8 или 12 часов, навыки, транспорт, доступное оборудование; есть работники без нужного навыка/транспорта и работник вне roster;
- tickets: фиксированные клиентские окна, длительность, тип работ, оборудование, район/город, координаты, участок, `request_type_hd`, `received_at`; включить пустые/неизвестные/конфликтные значения в отдельный отрицательный файл;
- day plans: начальная ревизия, зафиксированный roster, маршруты нескольких бригад и свободные промежутки разной длины;
- events: события прибытия, начала/окончания работ, обычные заявки и аварии в разные моменты дня; timestamps timezone-aware;
- geography: в одном CSV каждого участка смешать Москву и удалённые города (например, Домодедово и Кашира) как один регион; в отдельном регионе сделать географически соседние адреса для проверки жёсткого межучасткового запрета;
- road data: асимметричные времена/расстояния поездок, пробки или временные профили, чтобы порядок нельзя было проверить только прямым расстоянием; сохранить источник/stub marker.

## Сценарии итоговой приёмки

| ID | Сценарий и действие | Ожидаемый результат |
|---|---|---|
| S01 | Первичный импорт одного CSV региона с заявками Москвы и удалённых городов; повторить теми же строками как XLSX | Все строки получают один корректный `service_area_id`; город не порождает новый участок; CSV/XLSX дают эквивалентные данные, дубли при повторном импорте контролируются контрактом |
| S02 | Создать дневной план 12-часового и 8-часового профиля | Работают только интервалы выбранного дня; система не вычисляет цикл 2/2, 5/2, выходные или календарь |
| S03 | Планировать заявку бригадой другого участка, хотя адрес рядом; затем проверить адрес другого города того же участка | Межучастковое назначение отклонено с причиной; маршрут между городами одного участка разрешён при соблюдении остальных ограничений |
| S04 | Назначить заявку без требуемого навыка, транспорта, оборудования или вне смены | Кандидат не назначается; ответ содержит конкретные ограничения, общий validation применяется к solve, ручному пути и импорту |
| S05 | Подать обычную заявку, которая точно помещается между двумя остановками одного работника | Preview предлагает вставку; старые работники, назначения и взаимный порядок остановок не меняются; фиксированные окна соблюдены; показывается дорожный diff |
| S06 | Подать обычную заявку, которая не помещается ни в один свободный промежуток | Заявка не назначается, возвращены причины; существующие маршруты, назначения, геометрия и roster не перестроены |
| S07 | Проверить обычную вставку в начало и конец смены и в несколько потенциальных слотов | Выбирается допустимый вариант по фактической целевой функции; недопустимые варианты исключены по времени, окнам, навыкам/ресурсам/участку |
| S08 | Доставить новую обычную заявку во время `en_route` и `in_progress` у кандидата | Текущий этап не изменён; если подходящего свободного места нет без изменения старого порядка, заявка остаётся неназначенной |
| S09 | Подать заявку с `request_type_hd`, затем обычную заявку с аналогичным текстом, но без аварийного признака | Только признак источника определяет аварийную ветку; текст/название/высокий приоритет сами по себе не делают аварию |
| S10 | Авария поступает, когда доступная бригада завершила текущую работу и у неё есть будущее расписание | Preview может переставить только остаток дня; авария приоритетна; причины выбора, затронутые/вытесненные заявки, окна и прогноз реакции видны до apply |
| S11 | Авария поступает во время движения к текущей заявке | Бригада продолжает текущий этап; цель и уже начатое плечо не меняются; нельзя симулировать перенаправление посреди пути |
| S12 | Авария поступает во время выполнения работы | Работа завершается; аварийный маршрут строится только после фактического completion из известной точки и времени; таймер SLA продолжает отсчёт от `received_at` |
| S13 | Проверить аварийный норматив 60 и 120 минут: достижимый, пограничный и невозможный по дороге/окну случай | Метрика считается от времени поступления и согласованного события реакции; недостижимый норматив явно обозначен, не исправляется переносом окна |
| S14 | Авария имеет исходное окно 10:00–12:00; свободнее после 12:00. Отдельно подать заявку с исходным окном 12:00–14:00 | Первое окно остаётся 10:00–12:00 и конфликт/нарушение показывается; второе может использоваться как исходное окно. Никакого автоматического изменения customer window |
| S15 | Запустить отдельное сравнение 10:00–12:00 против гипотетического 10:00–14:00 | Baseline и эксперимент посчитаны на одинаковых данных/матрице; метрики сопоставимы; сценарий помечен как эксперимент и не изменяет live данные/apply |
| S16 | Повторить один event и apply с тем же idempotency key; отправить два конкурентных apply | Один логический результат и одна новая ревизия; конкурентный или stale apply не перезаписывает более новое состояние |
| S17 | Проверить `GeoJSON` маршрута до/после вставки и аварийной перестройки | Геометрия и порядковые stops соответствуют сохранённому плану/ревизии; старые ревизии неизменны; нет геометрии прежнего исполнителя после переноса |
| S18 | Вызвать известную невалидную конфигурацию участка/входных данных | Явная ошибка с сущностями/причиной; нет fallback назначения в участок preview, молчаливого пропуска или частичного сохранения |
| S19 | Повторить аварийный и обычный поток с работником вне первоначального roster | Такой работник не добавляется автоматически; возможная ручная форс-мажорная эскалация не входит в штатный сценарий и не тестируется как обычный успех |
| S20 | Проверить нотификации и историю после применения каждого потока | Маршрут, времена, назначение, event linkage и уведомление согласованы с одной новой ревизией; ошибка транзакции не оставляет частичный результат |

## Обязательные технические уровни

1. **Данные и importer:** schema/validation, CSV/XLSX equivalence, повторы импорта, даты/timezone, неизвестные enum, качество координат и участок.
2. **Python unit:** event classifier, SLA clocks, 8/12-часовой однодневный диапазон, eligibility, insertion positions, замороженный этап, неизменность окна, объяснения отказов.
3. **PostgreSQL integration:** миграции с нуля и на копии актуальной БД; применить/откатить согласно принятой практике; транзакционность назначений+маршрута+события+уведомления; ревизии, блокировки, stale preview, idempotency. БД недоступна — тест красный, не skip.
4. **Native planner E2E:** настоящий `/api/v1/solve`/replan и установленный OR-Tools; обычная вставка сохраняет существующий порядок, авария перестраивает будущее после safe point; сверить feasibility и решение независимым валидатором. Fixture planner не выдавать за native E2E.
5. **Geoapify:** отдельно проверить настоящий адаптер на контракте/ключе и ошибки провайдера; deterministic matrix stub использовать для воспроизводимых unit/E2E сценариев с явной маркировкой. Проверить cache key и направление матрицы.
6. **Bruno:** коллекции для создания дня, обычного preview/apply/no-slot, emergency preview/apply, события исполнения, окон, territory rejection, stale/idempotency и ошибок. Использовать тестовую БД и проверять ответы плюс побочные эффекты API/БД.
7. **Frontend/consumers:** проверить diff и объяснения, разные статусы обычной вставки/аварийного safe-point, и невозможность подменить серверную категорию через UI.
8. **GitHub Actions:** workflow должен реально запускать lint/type checks, тестовые зависимости, PostgreSQL, native solver, необходимые Bruno/API прогоны и синтетические сценарии; failure любого обязательного сервиса должен проваливать job. Проверить фактический завершённый run по commit SHA, а не только YAML.

## Метрики и анализ качества

Сравнивать исходный план и итоговый план на одинаковой матрице и исходном roster. Для каждого сценария записывать число выполненных/неназначенных заявок, аварийную реакцию, число нарушенных клиентских окон и смен, время/дистанцию дороги, простои/ожидание, дополнительный пробег, число изменённых будущих остановок и причины изменений. Не объявлять улучшение по одному сокращению километров, если ухудшились покрытие, клиентские окна, SLA или число изменений.

Для обычной заявки отдельно доказать инвариант: множество существующих назначений и их относительный порядок до/после совпадает. Для аварии отдельно доказать: замороженный текущий этап совпадает, все остальные изменения находятся после safe point. Плохое или невыполнимое решение должно диагностироваться, а не заменяться фиктивным успешным планом.

## Чек-лист запуска и отчёт

Выполняющий приёмку сохраняет в отчёте:

- commit SHA, ОС, версии Python/Node/solver/DB, timezone и команды запуска;
- manifest synthetic data: seed, размер, checksum и marker источника дорожных матриц;
- миграции и доступность PostgreSQL;
- результаты каждого S01–S20: passed/failed, фактический ответ и проверенные DB-инварианты;
- команды lint/unit/API/DB/native planner/Bruno и итоговые числа тестов;
- GitHub Actions URL, branch/commit, все обязательные jobs и завершённый статус;
- список отличий ожидаемого/фактического, заведённые дефекты и конкретные ограничения;
- результат проверки чистого запуска по README и итоговый diff.

Нельзя отмечать полный успех, если любой S-сценарий пропущен, БД недоступна, native planner заменён фикстурой, CI workflow только прочитан, либо синтетические данные не прошли проверку схемы и контрольных сумм. Для любой незавершённой части указать причину и не называть систему полностью принятой.

## Итоговые критерии приёмки

- Все задачи T плана 1–4 выполнены и критерии каждой подтверждены тестом или проверяемым артефактом.
- Все сценарии S01–S20 имеют фактический результат; критические инварианты проверены на данных и сохранённой истории.
- CSV/XLSX, API, DB, native planner, Geoapify integration, Bruno и GitHub Actions согласованы по одному контракту.
- Чистый запуск воспроизводится по README; все обязательные проверки действительно проходят локально и в CI.
- Synthetic acceptance dataset достаточно разнообразен для положительных, граничных, конфликтных и неразрешимых случаев, воспроизводим по seed и не содержит реальных персональных данных.
- Итоговый отчёт указывает реальные результаты и остаточные ограничения; фиктивное прохождение/пропуск не допускается.
