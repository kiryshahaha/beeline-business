# План 2: районы, участки и дневной состав бригад

## Цель

Согласовать территориальные назначения и состав работников однодневного плана с уточнениями экспертов:

- географический район — часть города; участок может включать несколько географических районов;
- межучастковые назначения запрещены;
- внутри одного участка бригада может выполнять заявки из любого входящего в него района и перемещаться между городами, если они включены в тот же участок;
- город, район и офис сами по себе не заменяют идентификатор участка;
- в scope планирования входит один отдельно взятый день;
- новый спрос не должен автоматически расширять первоначальный состав дня за счёт сотрудников, не включённых в дневной план.

Этот документ выполняется параллельно с [планом 1: смены и аварии](АЛЕРТРАБАОТАБЭКЕННД.md). Обновлённое понимание смен: 2/2 — 12-часовой интервал, 5/2 — 8-часовой интервал в выбранный день. План 2 использует указанный интервал и не реализует ротацию по календарным дням, выходные по циклу или производственный календарь.

## Текущее состояние проекта

- Кандидаты и ручное назначение также проверяют `service_area_id`.
- Географический район, город и участок — разные понятия. Город не используется как обязательная граница маршрута; это соответствует уточнению экспертов.
- Район в текущей модели может быть частью адресной иерархии. `service_area_id` — операционная граница, к которой привязаны адреса, подразделения и планы дня.

- `replan/preview` выбирает работников участка без отдельного сохранённого снимка исходного дневного состава. Это способно расширить пул кандидатов после первой публикации.
- Ротационный календарь 2/2/5/2 в проекте отсутствует и, согласно последнему уточнению, в эту работу добавлять его не нужно.

## Предметные правила

1. **Участок — единственная жёсткая территориальная граница распределения.** Заявка и бригада должны относиться к одному `service_area_id`.
2. **Районы входят в участки.** Если два географических района закреплены за одним участком, бригада участка может обслуживать оба.
3. **Города не делят участок автоматически.** Москва и Домодедово могут быть одной территорией планирования, если данные относят их к одному участку.
4. **Географическая близость не отменяет разные участки.** Соседние адреса или пересекающиеся географические зоны не дают права назначать бригаду другого участка.
5. **Неизвестный участок нельзя считать участком текущего запроса.** Неоднозначные/конфликтные данные блокируют назначение с явной причиной.
6. **Рабочий интервал — только на выбранный день.** Его длительность приходит из согласованного с планом 1 профиля: 12 часов для режима 2/2 или 8 часов для режима 5/2; рабочие и выходные даты по циклу здесь не вычисляются.
7. **Состав дня фиксируется при первоначальной публикации.** Replan может менять маршруты и заявки внутри этого состава, но не добавляет всех работников участка автоматически.
8. **Работник вне первоначального состава не привлекается сам по себе из-за новой заявки или аварии.** Возможную форс-мажорную эскалацию оформлять отдельным решением после уточнения процесса; обычный solver не должен обходить ограничение.

## План работ

### 1. Зафиксировать модель «район → участок» и источник участка заявки

- Описать словарь/связи географических районов и участков так, чтобы участок мог объединять несколько районов.
- Оставить `service_area_id` каноническим ID для planning snapshot, ревизии дня и worker eligibility.
- Уточнить, откуда берётся участок заявки: файл/набор данных, явно выбранный обслуживающий офис или ручной выбор участка. Если сохраняется офис приёма, валидировать его участок; не вычислять область по названию города.
- Для импортируемых файлов закреплять все районы файла за единым участком только при подтверждённом наборе данных. Адрес в другом городе не должен автоматически создавать новый участок.
- Геокодирование должно возвращать координаты и адресные справочники; оно не должно решать межучастковое распределение по городу или близости.

**Готово, когда:** каждый ticket имеет однозначный участок, а разные районы/города одного участка остаются совместимыми.

### 2. Проверить связность офиса, подразделения, бригады и работника

- Сверять участок заявки с участком обслуживающего офиса/набора данных.
- Сверять `Division.service_area_id`, участок офиса бригады, `Worker.service_area_id` и участок склада работника.
- Унаследовать участок работника из его единственной активной бригады только при согласованном состоянии связей.
- Удалить fallback, который молча относит работника без определённого участка к участку выбранного preview.
- Подготовить диагностический отчёт по существующим строкам с пропусками и расхождениями. Автоматически переносить бригаду или заявку между участками нельзя.
- Возвращать понятную причину с конфликтующими ID, например `service_area_missing` или `service_area_configuration_mismatch`.

**Готово, когда:** любое противоречие блокирует назначение до исправления данных и не разрешается выбором значения по умолчанию.

### 3. Проверить межучастковое ограничение во всех путях

Единая проверка участка должна покрывать:

- обычный planning preview и replan preview;
- ручное назначение работника и перенос между бригадами;
- назначение бригады заявке;
- импорт контрольного распределения CSV/XLSX;
- API создания/сохранения маршрута и его остановок;
- применение preview и создание ревизии дня.

Набор заявок из двух участков должен отклоняться до вызова solver. Бригада другого участка не должна становиться кандидатом даже при короткой дороге. Внутри участка выбор районов и городов остаётся за оптимизатором и временными окнами.

**Готово, когда:** межучастковое назначение одинаково запрещается автоматикой, ручными API, импортом и прямой записью маршрута.

### 4. Сохранять дневной roster и не расширять его при replan

- Определить исходный roster дня по выбранным и допущенным к первому плану работникам. Он не равен только инженерам, получившим хотя бы одну остановку.
- Сохранять roster вместе с первой опубликованной ревизией дня, включая работников без назначенного визита, участок и однодневный интервал смены из контракта плана 1.
- При повторном replan брать тот же roster, ограничивать его участком и текущей доступностью, учитывать активные/замороженные этапы работ.
- Не выполнять в replan текущий поиск всех сотрудников участка как способ пополнить штатный состав дня.
- Если у старой ревизии roster отсутствует, восстанавливать его только из связанного snapshot первоначального preview. Если это невозможно, не подставлять весь участок; вернуть явную ошибку и потребовать безопасного утверждения состава.
- Изменение исходного roster оформлять явным действием диспетчера и новой ревизией, а не следствием появления нового ticket.

**Готово, когда:** новый спрос не добавляет в штатный план сотрудника, который не был включён в исходный дневной roster.

### 5. Разделить обычный режим и форс-мажор

Эксперты допускают возможность привлечь дополнительного сотрудника в исключительной ситуации, но не требуют автоматически привлекать работников в каждый выходной. Так как scope — один отдельно взятый день и отдельный производственный календарь исключён, базовая реализация не вычисляет, у кого по циклу выходной.

Если позднее потребуется эскалация:

- добавить отдельную операцию ручного расширения состава дня;
- требовать полномочия, обоснование и явное подтверждение;
- применять участок, квалификацию, транспорт, оборудование и однодневное временное окно как обычные ограничения;
- записывать автора, причину, старый и новый roster в аудит и ревизию;
- не делать общего `force=true` и не запускать такую эскалацию автоматически при аварии.

**Готово, когда:** базовый replan неизменно соблюдает дневной roster; исключение невозможно вызвать случайно.

### 6. Подтвердить рациональность маршрутов внутри участка

- Использовать реальные профили времени и расстояния Geoapify для всех точек участка.
- Не добавлять hard constraint по городу или географическому району.
- Проверить на сценариях с несколькими районами/городами, что планировщик минимизирует фактический путь в рамках более старших целей и фиксированных окон.
- Для примера «Москва → Домодедово → Москва → Домодедово» сравнить допустимые порядки остановок. Показывать маршрутные времена и причины выбора; не вводить запрет на такую последовательность, если её требуют временные окна или другие ограничения.

**Готово, когда:** межгородской маршрут в одном участке разрешён и оценивается фактическими дорожными затратами, а межучастковый — всегда запрещён.

## Параллельная работа с планом 1

План 1 реализует однодневный интервал смены: режим 2/2 — 12 часов, режим 5/2 — 8 часов. План 2 не создаёт таблиц циклического графика и использует только готовые часы выбранного дня.

Владение изменениями:

- **План 1:** модель и API однодневной смены, значения 12/8 часов, классификация `request_type_hd`, время поступления и аварийный SLA.
- **План 2:** правила `район → участок`, согласованность офиса/подразделения/бригады/работника, территория и сохранение исходного roster дня.
- **Общие точки:** `planning/repository.py`, `planning/eligibility.py`, `planning/service.py`, `planning/policy.py`, `planning/schemas.py`, `tickets/service.py`, Alembic migrations и интеграционные planning tests.

Для общих файлов назначить одного интегратора: параллельные исполнители готовят отдельные функции/тесты и не редактируют одни и те же точки вызова одновременно. Контракт однодневной смены из плана 1 — передавать уже разрешённые `workshift_start`/`workshift_end` выбранного дня; план 2 не дублирует правила вычисления 12/8 часов. Миграции получают разные Alembic revision ID и проверяются в единой истории после объединения.

Последовательность объединения: сначала согласовать профиль смены и resolver плана 1; затем подключить его к проверке исходного roster; после этого интегрировать territory validator в общие точки preview/replan/apply. Финальная проверка выполняется на совместном состоянии, потому что каждый план отдельно не проверяет пересечение roster, участка и времени смены.

## Синтетические данные и проверки

### Территориальные случаи

- Один участок содержит несколько географических районов Москвы: назначения между районами разрешены.
- Москва и Домодедово или Кашира размечены одним участком: межгородской маршрут разрешён.
- Адреса в одном городе размечены разными участками: кросс-назначение запрещено.
- Два файла разных районов относятся к одному подтверждённому участку; импорт сохраняет общий `service_area_id`.
- Несогласованные участки у ticket, worker, brigade, division, office и stock office дают конкретную ошибку.
- Пустой участок не наследуется из запроса.

### Дневной roster и смена

- Первый план сохраняет всех выбранных работников, включая работников без остановок.
- Replan после новой обычной заявки сохраняет состав и интервал смены.
- Replan после аварии в середине дня не выбирает остальных работников участка.
- Изменение времени/состава после preview делает его устаревшим; новый apply остаётся атомарным и создаёт следующую ревизию.
- Однодневная смена 12/8 часов берётся из контракта плана 1; тесты не моделируют недельные циклы и не определяют выходные.

### Уровни проверок

- Unit-тесты разрешения участка и сравнения связей office/division/brigade/worker/ticket.
- PostgreSQL migration и API-тесты межучастковых отказов, дневного roster и восстановления старых ревизий.
- Native OR-Tools интеграция: несколько районов/городов одного участка в одном решении, межучастковый набор отклонён до solver.
- Bruno: успешный same-area сценарий, отказ cross-area, replan без расширения roster, apply новой ревизии.
- GitHub Actions с обязательной тестовой PostgreSQL и настоящим planner; отсутствие БД не считается skip, fixture planner не считается native E2E.

2. Проверить существующие связи офиса, района, участка, подразделения, бригады, работника, адреса и склада; подготовить отчёт конфликтов.
3. Реализовать единый строгий resolver участка и убрать молчаливое наследование участка из preview.
4. Применить проверку во всех путях назначения, ручного переноса, импорта, маршрутов и apply.
5. Зафиксировать дневной roster на первой опубликованной ревизии, включая выбранных работников без визитов.
6. Ограничить replan исходным roster; использовать однодневные часы смены из плана 1.
7. Добавить синтетические межрайонные/межгородские и cross-area сценарии, DB/native solver/Bruno проверки и CI.
8. Обновить документацию модулей по понятиям «район», «участок», «город» и по составу однодневного плана.
9. Форс-мажорное расширение roster оставить отдельной будущей задачей с явным подтверждением процесса.

## Критерии готовности

- Один `service_area_id` может включать несколько географических районов и городов.
- Город и район не используются как hard constraint для solver.
- Ни автоматическое, ни ручное назначение не пересекает границы участков.
- Пропущенные или противоречивые связи территории не исправляются молчаливым fallback.
- Первая ревизия дня фиксирует исходный roster, даже если отдельные выбранные работники получили ноль визитов.
- Новый ticket и авария не добавляют сотрудников участка за пределами исходного roster.
- Интервал смены одного дня соответствует выбранному режиму 12/8 часов; циклический календарь и выходные не моделируются.
- Объединённые изменения планов 1 и 2 проходят PostgreSQL, native solver, Bruno и GitHub Actions проверки.
