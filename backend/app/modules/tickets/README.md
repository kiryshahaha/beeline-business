# Заявки

`tickets` хранит место, район обслуживания, целевую бригаду, вид работ, статус, окно визита, плановые начало/конец и оценочную/фактическую длительность. `brigade_id` допускает `NULL`, пока диспетчер не разрешил неоднозначность. Статусы: planned, in_progress, completed, wont_fix. Плановые времена либо оба отсутствуют, либо образуют корректную пару.

При создании заявки сервер берёт координаты из `locations.latitude` и
`locations.longitude`. Если заданы обе координаты и настроен `GEOAPIFY_API_KEY`,
Geoapify reverse geocoding возвращает район, который сервер сопоставляет со
справочником города и `service_areas`. Когда район не найден у провайдера или в
справочнике, заявка сохраняет адресный район и остаётся без целевой бригады.
Без координат или ключа сервер использует район адреса. Для района с одной
бригадой заявка получает её ID автоматически; при нескольких бригадах поле
остаётся пустым.

Явно переданный `service_area_id` (выбор диспетчера или набор данных) — участок заявки;
обратное геокодирование и адрес только заполняют его, когда участок не передан.
Ручное назначение (`PUT /assignees`) и его предпросмотр проверяют участок инженера тем
же модулем, что и планировщик: `service_area_mismatch`, `service_area_missing` или
`service_area_configuration_mismatch` в `detail.code` (в предпросмотре — в `violations`).
Участок инженера не выводится из офиса или адреса бригады.

Наблюдатель может выбрать бригаду через `PUT /api/v1/tickets/{id}/brigade` с телом
`{"brigade_id": 12}`. Бригада должна обслуживать район заявки, а её состав должен
совпадать с уже назначенным исполнителем. Для очистки выбора передайте
`{"brigade_id": null}`, пока у заявки нет исполнителя. Для заявки с исполнителем
сначала снимите назначение, затем меняйте или очищайте бригаду. Планировщик не
предложит заявку исполнителям разных бригад, пока район содержит несколько
бригад и диспетчер не выбрал одну.

Каждое изменение `tickets.assigned_worker_id` записывается в `ticket_assignment_events`
(заявка, прежний и новый исполнитель, автор, путь, время). Строку пишет триггер
`tickets_record_assignment`, поэтому историю не может пропустить ни один путь, включая
прямой SQL. Автора и путь сервис передаёт через `app.core.audit.set_assignment_origin`
(транзакционные настройки `app.actor_id`, `app.assignment_source`); без них изменение
записывается с источником `direct`. Исполнитель с такой историей не удаляется, а архивируется.

| Файл | Ответственность |
| --- | --- |
| `models.py` | Ticket, TicketAssignment, временные ограничения и индексы |
| `enums.py` | TicketStatus |
| `schemas.py` | Создание, чтение, фильтры, статус, целевая бригада и назначение исполнителя |
| `repository.py` | SQL заявок, адресов, видимости и уведомлений |
| `service.py` | Транзакции создания, выбора бригады, назначения исполнителя и смены статуса |
| `router.py` | Список/фильтры, чтение, создание, выбор бригады и рабочий процесс |

Хранение маршрута не меняет эти строки автоматически. Отдельных полей priority,
required_transport_type и внешнего ID заявки пока нет. Совместимый импорт отражает
эту схему; сценарные отметки в синтетических данных не подменяют эти поля.

Общий API описан в [backend README](../../../README.md); ограничения существующей
системы — в [аудите](../../../../docs/AUDIT_2026-09-18.md). Миграции находятся
в [migrations](../../../migrations/README.md), проверки — в [tests](../../../tests/README.md).
