# Планирование рабочего дня

Модуль связывает PostgreSQL, существующий planner (`POST /api/v1/solve`) и Geoapify.
Доступ к командам — у observer. Planner не получает адреса, персональные данные,
JWT пользователя или ключ Geoapify.

`GET /api/v1/planning/policy` возвращает действующие правила (`execution`) и
версионированный контракт кейса (`case_contract`, `activation=contract_only`).
Контракт нельзя включить через preview: API отвергает пользовательскую подмену правил.
Порядок целей контракта исполняет solver с политикой версии 2 (см. ниже); остальные
правила контракта считаются выполненными только там, где это прямо описано.
Подробная семантика и источники: [политика планирования](../../../../docs/PLANNING_POLICY.md).

## Процесс

1. `POST /api/v1/planning/preview`: передать дату, 1–50 ticket_ids, 1–20 worker_ids,
   allow_partial. Backend читает согласованный снимок, закрывает транзакцию, проверяет
   доступность, получает матрицы, вызывает planner и проверяет ответ независимо.
2. Geoapify возвращает дорожные сегменты для выбранного порядка точек. Если оценка
   сегмента расходится с матрицей, backend обновляет затронутые переходы и запускает
   solver ещё раз. Второе расхождение отклоняет preview до сохранения.
3. Preview сохраняется на 300 секунд; назначения, статусы, склад и маршруты пока не меняются.
4. `POST /api/v1/planning/plans/{UUID}/apply`: без тела или с `{}`. Backend проверяет
   актуальность входных данных и одним commit сохраняет маршруты, назначения,
   planned_start_at/planned_end_at и события уведомлений. Повтор возвращает ту же квитанцию.
5. `GET /api/v1/planning/plans/{UUID}` возвращает предложение или применённый план.
   Для применённого плана is_current сверяет снимок с текущей БД; исторические маршруты неизменны.

Новые планы возвращают полную `planning_policy`, сохранённую в JSONB вместе с
исходными данными, включая фактический лимит поиска. Чтение/apply используют
сохранённые параметры; смена текущих настроек не переписывает историю. У старых
планов без параметров `planning_policy=null`, их снимки не дополняются задним числом.
Неизвестная или неполная политика отклоняется перед применением с
`409 planning_policy_unsupported`. Для этого изменения миграция не требуется.
Новые предложения записывают политику версии 2. Снимки версии 1 читаются и
применяются с сохранёнными правилами, но заново через solver не рассчитываются.

## Перепланирование в течение дня

POST /api/v1/planning/areas/{service_area_id}/{route_date}/replan/preview применяет общую политику
системы без клиентского переключателя. Без новой аварийной заявки текущая ревизия
сохраняет исполнителя и точное обещанное время каждой незавершённой остановки;
новые обычные заявки могут занять только допустимый промежуток. Если существующая
остановка или новая заявка не помещается без изменения опубликованных визитов,
preview отвечает 409 ordinary_insert_no_gap и не сохраняет план.

Если появилась новая заявка категории emergency, существующий solver может
перестроить только незамороженный остаток дня. Инженер в en_route или in_progress
исключён из расчёта до события завершения текущей работы. Совместимый legacy endpoint
redirect возвращает 409 active_route_redirect_forbidden; повтор не меняет состояние.
Завершившийся инженер начинает остаток от подтверждённого адреса и времени.

Replan diff включает оценку реакции на аварию от received_at: прибытие, начало и
окончание работ, норматив 60/120 минут и выполнение service deadline. Это оценка
плана, а не телеметрия.

POST /api/v1/planning/areas/{service_area_id}/{route_date}/window-experiment
считает базовый и расширенный варианты на одном снимке. Ответ помечен
experimental=true и applied=false; операция не сохраняет preview/ревизию и не
изменяет окно заявки. Изменение клиентского окна выполняется отдельно через
execution API.

## Ограничения и целевая функция

Планируются неназначенные заявки planned и ещё не начавшиеся смены. Смена каждого
инженера рассчитывается на конкретную дату `route_date` с учётом графика (`2/2`, `5/2`) и
исключений (`worker_shift_exceptions`). Инженер на выходном дне исключается с кодом
`worker_day_off`. При перепланировании (`replan`) инженер с завершившейся сменой исключается
с кодом `worker_shift_ended`. Инженер с пересекающейся назначенной работой исключается.
У каждой заявки один исполнитель, начало и конец маршрута — офис бригады. Ночные смены
поддерживаются (переход через полночь), часовой пояс Europe/Moscow. Обслуживание целиком
помещается в окно и смену, включая возврат в офис.
Для аварийных заявок контролируется отдельный SLA реакции (`response_deadline_at`, 1–2 часа
от фиксации до начала работ `service_start_at`), передаваемый в payload решателя вместе
с источником поступления `intake_source` (`morning_assumption` или динамический `replan`).
Перепланирование остатка начавшегося дня сохраняет завершённые и начатые визиты из
текущей ревизии и рассчитывает только незавершённые назначения.

Для каждой задачи необходимы явно настроенные правила вида работ. Пустой список
требований допустим, отсутствие настройки — причина отказа. Учитываются все обязательные
навыки, активность оборудования, существующий резерв и склад офиса. Повторно списывать
или резервировать оборудование при apply не нужно. Позиции, уже выданные инженеру
или списанные, в резерв офиса не входят (см. [оборудование на руках](../appliances/README.md)).

Для нормы обслуживания берутся work_minutes + documents_minutes либо оценка заявки.
travel_minutes из справочника не добавляется: путь уже учтён Geoapify.

Цель решателя (политика версии 2) сравнивает допустимые планы лексикографически:
неназначенные аварии; минуты от поступления аварии до начала работ; неназначенные
подключения; все неназначенные; инженеры хотя бы с одним визитом (пустой маршрут не
считается); минуты в пути; визиты, переданные другому инженеру относительно текущего
назначения. Время и порядок визита в последний уровень не входят, их показывает
`replan_diff`. Вес каждого уровня больше наибольшей возможной суммы всех младших
уровней для этой задачи, поэтому взвешенная сумма ранжирует планы так же, как порядок
целей. Если такие веса не помещаются в 2^62, preview отклоняется с
`planning_limit_exceeded` (`limit=objective_cost_range`).

Planner возвращает разложение цели (`objective_components`), веса и итог; backend
пересчитывает разложение по проверенным маршрутам и отклоняет несовпадение с
`planner_invalid_response`. Preview отдаёт `objective_components`, ревизия дня хранит
их вместе с `planning_policy`; у ручной правки ревизии они `null`. OR-Tools с
ограничением времени может вернуть FEASIBLE: это лучший найденный план, без заявления
о доказанном глобальном оптимуме.

Транспорт: car→drive, walking→walk, bicycle→bicycle,
public_transport→approximated_transit. Для последнего возвращается предупреждение:
это приближённая оценка без реального расписания общественного транспорта.

## Причины и объяснения (T10)

Каждый отказ, исключение инженера и фактор визита имеет одну форму:

```json
{
  "code": "missing_skill",
  "category": "skill",
  "message": "Ни у одного из выбранных инженеров (4) нет навыка №7",
  "constraint": null,
  "ids": {"skill_ids": [7]},
  "observed": null,
  "required": {"skill_ids": [7]}
}
```

`code` стабилен для программы, `message` — короткий русский текст для диспетчера,
`constraint` — проверенное правило действующей политики, `ids` — связанные записи,
`observed`/`required` — фактическое и требуемое значение. Времена — ISO с МСК.

Категории: `data` (неизвестные или неполные данные), `ticket_state`, `availability`,
`skill`, `area` (участок обслуживания, бригада и офис резерва оборудования),
`transport`, `inventory`, `unreachable` (провайдер не нашёл дороги ни одним профилем),
`time` (окно и смена), `capacity`, `search` (лимит поиска), `mixed`; для факторов
визита также `policy` и `selection`.

`unassigned[]` — `{ticket_id, reason, candidates}`. `candidates` содержит причину для
каждого доступного инженера: сначала навыки, затем офис оборудования, окно и смена
(precheck), для прошедших precheck — проверки по матрице времени решателя:

1. Визит как единственная остановка инженера. Если даже так дороги нет, инженер
   прибывает после конца окна или не завершает маршрут до конца смены — это
   доказанная причина для этого инженера (`unreachable_by_transport`,
   `address_unreachable`, `arrival_after_window`, `return_after_shift_end`).
2. Вставка в рассчитанный маршрут на каждую позицию. Нашлось место — решатель не выбрал
   его за лимит поиска: `feasible_slot_missed`, у инженера `slot_available`. Места нет —
   `no_slot_in_computed_plan`, у инженера `route_full`. Это не доказательство
   невозможности: полная перестановка маршрутов дня не проверяется.

Диагностика только объясняет план и ничего в нём не меняет. Её объём ограничен
контрактом решателя (не более 70 узлов).

Каждый визит маршрута содержит `factors`: навыки, транспорт и время в пути, начало в
окне, комплект оборудования, действующая политика приоритетов и число инженеров,
прошедших проверку. Текст не называет инженера лучшим: при нескольких кандидатах
выбор сделан по общей цели плана без отдельного сравнения для этой заявки.

`GET /plans/{id}` также возвращает `workers`: для каждого инженера расчёта бригаду и офис
из входного снимка (как было при расчёте) и текущие ФИО, роль и `archived_at`. Смена роли,
архив или новый состав бригады не переписывают историю плана. Архивный инженер
исключается из нового расчёта с причиной `worker_archived`; сам снимок хранит список
архивных ID только когда они есть, поэтому отпечатки прежних планов не меняются.

`metrics` — входные, допустимые, назначенные и неназначенные заявки, доступные и
использованные инженеры, расстояние, минуты пути, работы и ожидания, число отказов по
категориям. В `metrics.routing` входят запросы, ячейки матрицы, этапы, попадания кэша,
профили, повторы, источники оценок и безопасные коды ошибок. `outcome`: `complete`,
`partial` или `empty`.

Матрицы и дорожные участки хранятся только в памяти процесса: LRU ограничен 256
записями и 16 МиБ, срок хранения по умолчанию — 300 секунд. Ключ включает провайдера,
профиль, упорядоченные координаты с точностью 6 знаков и параметры маршрута. В записи
кэша сохраняются срок истечения и источник ответа. Для 429 и 5xx backend делает до
двух повторов, соблюдая `Retry-After`; отмена и общий лимит preview в 60 секунд
останавливают ожидание.

Live smoke запускается только по запросу: `GEOAPIFY_LIVE_SMOKE=1 GEOAPIFY_API_KEY=…`
из каталога `backend`, команда `python -m unittest tests.test_geoapify_live`. Проверка
сверяет профиль `drive`, форму матрицы и GeoJSON, не фиксируя точную длительность.

`resource_estimate` появляется, когда есть заявки `no_slot_in_computed_plan`. Жадная
вставка в пустые маршруты копий реальных инженеров (те же навыки, офис, смена и
транспорт; одинаковые инженеры дают одну копию) при неизменных рассчитанных
маршрутах. Не более 50 000 проверок расписания; при остановке по лимиту `complete=false`.
Это оценка (`is_estimate=true`), а не доказанный минимальный штат.

### Пустой план и ошибки

Если ни одна заявка не назначена (все отклонены precheck или решатель никого не
включил), preview возвращает обычный `201` с `outcome="empty"`, метриками и причинами.
Такой preview сохраняется, чтобы экран мог открыть его по `plan_id`; `solver_status=null`,
если до решателя дело не дошло. Apply обычного пустого плана отвечает
`409 plan_has_no_assignments`; replan может опубликовать пустой остаток и снять прежние
назначения отдельными событиями `unassign`.

`allow_partial=false` по-прежнему даёт `422 incomplete_plan`; `unassigned` в ошибке имеет
ту же структуру. Сбои не выдаются за пустой план: решатель без решения —
`503 planner_not_solved` (`retryable=true`), тайм-аут — `504`, неверный ответ
провайдера или решателя — `502`. План в этих случаях не сохраняется.

Планы, сохранённые до T10, читаются: строковые коды превращаются в структуру без
подробностей, `metrics` отсутствует, у визитов нет `factors`.

## Текущий план дня и ревизии (T09)

План дня определяется парой `(service_area_id, route_date)`. У пары есть ровно одна
текущая ревизия: частичный уникальный индекс `uq_day_plan_revisions_current` не
позволяет существовать двум одновременно актуальным версиям одного участка и дня.
Публикация переводит маркер `is_current` внутри той же транзакции, что и запись
маршрутов, поэтому два apply не дают двух актуальных планов: второй ждёт блокировку
строки и нумеруется следующим.

Три номера остаются разными понятиями: UUID preview (`plan_id`), номер ревизии дня
(`revision`) и порядковый номер маршрута инженера за сутки (`routes.route_number`).

Каждая ревизия хранит `plan_state` — обещанные визиты и метрики на момент публикации.
Более поздняя ревизия его не переписывает, поэтому исторический маршрут продолжает
отвечать той геометрией и теми временами, с которыми был применён. Фактический
прогресс выполнения живёт в модуле execution и в обещанное время не подмешивается.

| Поле ревизии | Значение |
|---|---|
| `revision`, `previous_revision` | номер в рамках участка и дня и предыдущий номер |
| `superseded_at`, `superseded_by_revision` | когда и какой ревизией заменена |
| `reason` | `plan_applied`, `worker_redirected`, `manual_edit`, `event_replan` |
| `actor_id`, `event_id`, `plan_id` | кто применил, какое событие и какой preview |
| `effective_at` | с какого момента ревизия действует |
| `plan_state` | визиты `{ticket_id, worker_id, route_id, sequence, arrival_at, service_start_at, service_end_at}` и метрики |
| `diff` | изменения относительно предыдущей ревизии; `diff.roster` — кто добавлен в состав дня |
| `roster` | состав дня: `{worker_id, service_area_id, workshift_start, workshift_end, source}` каждого допущенного инженера, в том числе без визитов; `null` у ревизий до миграции 0031 |

`service_area_id` задаёт единственную идентичность ревизии. Перенаправление инженера
публикует новую ревизию той же зоны; ID зоны берётся из запроса и проверяется по
справочнику `service_areas`.

### Операции

| Запрос | Ответ |
|---|---|
| `GET /planning/areas/{service_area_id}/{route_date}/current` | текущая ревизия с визитами и diff; 404 `day_plan_not_found`, если планов дня ещё не было |
| `GET /planning/areas/{service_area_id}/{route_date}/revisions` | вся история по возрастанию номера |
| `GET /planning/areas/{service_area_id}/{route_date}/revisions/{revision}` | конкретная ревизия; `is_current=false` прямо помечает её исторической |
| `GET /planning/areas/{service_area_id}/{route_date}/diff?base=&target=` | сравнение; без параметров — текущая против предыдущей |

Diff показывает `added`, `removed`, `changed` (исполнитель, порядок, `arrival_at`,
`service_start_at`, `service_end_at`), `unchanged_ticket_ids`, изменение метрик с
дельтой и `roster` (`{added, removed}` или `null`, если состав не менялся). Все команды
доступны observer.

`GET /routes` и `GET /routes/{id}` добавляют `service_area_id`, `day_revision` и
`is_current_plan`. `is_current_plan=null` означает, что маршрут сохранён вне
планировщика и ни одна ревизия его не заявляет; `false` — маршрут принадлежит
заменённой ревизии, то есть это история, а не действующий план.

### Актуальность входных данных

`input_fingerprint` считается не только по выбранным ticket_ids и worker_ids: снимок
содержит `area_scope` — все заявки участка на эту дату (id, статус, revision,
исполнитель) и число с последним id рабочих событий дня. Поэтому новая аварийная
заявка, отмена или событие в том же участке делают предложение устаревшим, и apply
отвечает `409 plan_stale`, а не применяет расчёт, мимо которого день уже ушёл.
TTL preview и идемпотентность повторного apply не изменились.

### Перепланирование остатка дня (T06)

`POST /api/v1/planning/areas/{service_area_id}/{route_date}/replan/preview` принимает
`base_day_revision` текущего плана и `allow_partial`; без опубликованной ревизии дня
endpoint отвечает `404 day_plan_not_found`, поскольку ему нужны обещания для сравнения
и заморозки уже начатых визитов. Backend в одном снимке БД читает
заявки участка с датой визита, инженеров состава дня (`roster` текущей ревизии), события
исполнения и текущую ревизию, после чего передаёт допустимый остаток в тот же solver, что
и обычный preview.

Ответ содержит обычные маршруты и `replan_diff`: номер исходной ревизии, новые,
удалённые, изменённые и неизменные визиты. Preview ничего не назначает. Диспетчер
публикует его через `POST /api/v1/planning/plans/{plan_id}/apply`; атомарное применение
создаёт одну ревизию с причиной `event_replan`. Повтор возвращает прежнюю квитанцию,
изменившаяся заявка, событие или ревизия дают `409 plan_stale` либо `409 day_revision_stale`.

Завершённые, выполняемые и уже en_route визиты остаются в плане с прежними обещанными
временами, пока заявка не отменена. Отменённый визит исчезает из новой ревизии и
остаётся в истории старой; если инженер уже выехал, состояние дня сохраняет текущий
переезд до подтверждённого перенаправления. Для следующего маршрута берётся последняя
подтверждённая точка либо пункт назначения начатого переезда. Если инженер ещё не
отправился, расчёт использует его начальную точку. Инженер с незаконченной работой
допускается к расчёту после `expected_available_at`; если время освобождения не сообщено
и старый план уже не задаёт будущий конец работы, solver его исключает. Для события
недоступности без ETA сервис задаёт конец смены; указанное диспетчером время внутри
смены используется как
момент возврата.

Заявки, которые solver не назначил, не переходят в `cancelled`: для назначенных,
отправленных или ещё не начатых задач пишется событие `unassign`, очищается исполнитель
и прежнее обещанное время. Завершение заявки по-прежнему списывает оборудование через
существующий журнал исполнения; повтор события с тем же ключом не списывает его второй
раз.

## Настройка и ошибки

Миграции 0012/0013 обязательны. PLANNING_ENABLED=true,
PLANNER_BASE_URL, одинаковый PLANNER_SERVICE_TOKEN в двух сервисах,
GEOAPIFY_API_KEY — в backend. Полный пример: ../../../.env.example.

Расчёт ограничен 70 логическими узлами, 20 000 ячеек матриц, двумя preview на процесс,
4 одновременными запросами провайдера, 5 секундами поиска и 60 секундами суммарного расчёта.
Запрос preview ≤64 KiB; ответ каждого upstream ≤4 MiB после распаковки.

422 — некорректные ID/ограничения или неполный план при allow_partial=false;
409 — истёкший/устаревший/пустой план; 502 — неверный ответ провайдера или решателя;
503 — выключенная/недоступная подсистема либо занятые слоты; 504 — тайм-аут.
SQL, ключи и ответы внешних сервисов в публичные ошибки не включаются.

Изменяющие предметные данные операции берут общий PostgreSQL advisory lock
из core/planning_guard.py перед блокировками строк. Сетевых запросов под ним нет.
Прямое изменение БД сторонним процессом должно соблюдать этот же протокол;
иначе гарантировать отсутствие гонки с apply невозможно.

## Участок и состав дня (план 2)

Участок обслуживания (`service_area_id`) — единственная жёсткая территориальная граница.
Город, район и близость адресов сами по себе ничего не разрешают и не запрещают: заявки
одного участка в Москве и Домодедово попадают в один расчёт, а время между ними решает
дорожная матрица и окна. Заявки разных участков в одном расчёте — `422
multiple_service_areas` до вызова solver.

Участок определяется одним модулем `service_areas/territory.py` для всех путей: preview,
replan, apply, ручное назначение и его предпросмотр, смена бригады заявки, состав бригады
и прямое сохранение маршрута `POST /routes`. Участок заявки — её собственный (набор
данных или выбор диспетчера), иначе участок здания адреса; обратное геокодирование
больше не перекрывает явно выбранный участок. Участок инженера сверяется по всем
источникам: профиль, подразделение бригады, явный участок офиса бригады и склада.

| Код | Когда |
|---|---|
| `service_area_missing` | ни один источник не указывает участок; участок запроса не подставляется |
| `service_area_configuration_mismatch` | источники противоречат друг другу; в `sources` все значения |
| `service_area_mismatch` | участок инженера (бригады) не совпадает с участком заявки или плана |

Выбранный диспетчером инженер с такой ошибкой отклоняет preview целиком (`422`, в
`workers` — источники). В replan тот же инженер из состава дня исключается с причиной, а
расчёт остальных продолжается. `GET /api/v1/service-areas/consistency` (observer)
перечисляет инженеров, бригады и открытые заявки с такими связями; ничего не переносит.

Состав дня (`roster`) фиксируется первой публикацией: все выбранные в preview инженеры с
их участком и сменой на момент допуска. Replan берёт кандидатов только из него и
использует записанные часы смены; новая заявка или авария никого не добавляет, apply
дополнительно отклоняет предложение с инженером вне состава (`409 day_roster_expanded`).
Состав расширяет только явное действие диспетчера — preview/apply с выбранными инженерами
или ручное назначение; такая ревизия показывает `diff.roster.added`. Для ревизий до 0031
состав восстанавливается только из снимков preview, с которыми они применялись, и из их
опубликованных визитов; если восстановить нечего — `409 day_roster_unrecoverable`, весь
участок не подставляется. Форс-мажорный вызов инженера вне состава отдельной операцией
не реализован.
