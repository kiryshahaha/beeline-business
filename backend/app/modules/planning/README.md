# Планирование рабочего дня

Модуль связывает PostgreSQL, существующий planner (`POST /api/v1/solve`) и Geoapify.
Доступ к командам — у observer. Planner не получает адреса, персональные данные,
JWT пользователя или ключ Geoapify.

`GET /api/v1/planning/policy` возвращает действующие правила (`execution`) и
версионированный контракт кейса (`case_contract`, `activation=contract_only`).
Контракт нельзя включить через preview: API отвергает пользовательскую подмену правил.
Его наличие не означает, что приоритеты/SLA/открытые маршруты уже поддержаны solver.
Подробная семантика и источники: [политика планирования](../../../../docs/PLANNING_POLICY.md).

## Процесс

1. `POST /api/v1/planning/preview`: передать дату, 1–50 ticket_ids, 1–20 worker_ids,
   allow_partial. Backend читает согласованный снимок, закрывает транзакцию, проверяет
   доступность, получает матрицы, вызывает planner и проверяет ответ независимо.
2. Geoapify возвращает дорожные сегменты для выбранного порядка точек. Если более
   точная оценка пути нарушает рассчитанное расписание, preview отклоняется.
3. Preview сохраняется на 300 секунд; назначения, статусы, склад и маршруты пока не меняются.
4. `POST /api/v1/planning/plans/{UUID}/apply`: без тела или с `{}`. Backend проверяет
   актуальность входных данных и одним commit сохраняет маршруты, назначения,
   planned_start_at/planned_end_at и события уведомлений. Повтор возвращает ту же квитанцию.
5. `GET /api/v1/planning/plans/{UUID}` возвращает предложение или применённый план.
   Для применённого плана is_current сверяет снимок с текущей БД; исторические маршруты неизменны.

Новые планы возвращают полную `planning_policy`, сохранённую в JSONB вместе с
исходными данными, включая фактический лимит поиска. Чтение/apply используют
сохранённые параметры; смена текущих настроек не переписывает историю. У старых
планов без параметров `planning_policy=null`, их снимки не дополняются задним числом.
Неизвестная или неполная политика отклоняется перед применением с
`409 planning_policy_unsupported`. Для этого изменения миграция не требуется.

## Ограничения и целевая функция

Планируются неназначенные заявки planned и ещё не начавшиеся смены. Инженер с
пересекающейся назначенной работой исключается. У каждой заявки один исполнитель,
начало и конец маршрута — офис бригады. Ночные смены поддерживаются, часовой пояс
Europe/Moscow. Обслуживание целиком помещается в окно и смену, включая возврат в офис.
Перепланирование уже начавшегося дня с сохранением выполненных участков пока не реализовано.

Для каждой задачи необходимы явно настроенные правила вида работ. Пустой список
требований допустим, отсутствие настройки — причина отказа. Учитываются все обязательные
навыки, активность оборудования, существующий резерв и склад офиса. Повторно списывать
или резервировать оборудование при apply не нужно.

Для нормы обслуживания берутся work_minutes + documents_minutes либо оценка заявки.
travel_minutes из справочника не добавляется: путь уже учтён Geoapify.

Цель решателя: сначала больше завершённых заявок, затем меньше минут в пути.
Штраф пропуска одной заявки V×H+1 больше возможной суммарной поездки всех инженеров.
Фиксированная стоимость использования работника равна нулю. OR-Tools с ограничением
времени может вернуть FEASIBLE: это допустимое решение, без заявления о доказанном глобальном оптимуме.

Транспорт: car→drive, walking→walk, bicycle→bicycle,
public_transport→approximated_transit. Для последнего возвращается предупреждение:
это приближённая оценка без реального расписания общественного транспорта.

## Файлы

| Файл | Ответственность |
|---|---|
| router.py, schemas.py | Авторизация, HTTP DTO, ограничения размера и числа запросов |
| repository.py, snapshot.py | Согласованный снимок предметных данных и его SHA-256 |
| policy.py | Неизменяемые правила текущего расчёта, проверка поддерживаемой версии, сохранение параметров |
| case_policy.py, case_policy_v1.json | Проверяемый контракт кейса, происхождение правил и эталонное сравнение целей; не второй solver |
| eligibility.py | Смены, окна, квалификация, оборудование, причины исключения |
| matrices.py | Дедупликация координат, направленные блоки 25×25 для каждого профиля |
| planner_client.py, solver_contract.py | Внутренний HTTP-контракт, token, timeout, проверка ответа |
| validation.py | Независимая проверка назначения, расписания, пропусков и метрик |
| geometry.py | Дорожные MultiLineString, сопоставление переходов и проверка времени |
| service.py | Оркестрация preview и атомарного apply, TTL и повторные запросы |
| models.py | planning_plans и planning_plan_routes |
| async_utils.py, errors.py | Ограниченный параллелизм и безопасные публичные ошибки |

## Настройка и ошибки

Миграции 0012/0013 обязательны. PLANNING_ENABLED=true,
PLANNER_BASE_URL, одинаковый PLANNER_SERVICE_TOKEN в двух сервисах,
GEOAPIFY_API_KEY — в backend. Полный пример: ../../../.env.example.

Расчёт ограничен 70 логическими узлами, 20 000 ячеек матриц, двумя preview на процесс,
4 одновременными запросами провайдера, 5 секундами поиска и 60 секундами суммарного расчёта.
Запрос preview ≤64 KiB; ответ каждого upstream ≤4 MiB после распаковки.

422 — некорректные ID/ограничения или отсутствие выполнимых назначений;
409 — истёкший/устаревший план; 502 — неверный ответ провайдера или решателя;
503 — выключенная/недоступная подсистема либо занятые слоты; 504 — тайм-аут.
SQL, ключи и ответы внешних сервисов в публичные ошибки не включаются.

Изменяющие предметные данные операции берут общий PostgreSQL advisory lock
из core/planning_guard.py перед блокировками строк. Сетевых запросов под ним нет.
Прямое изменение БД сторонним процессом должно соблюдать этот же протокол;
иначе гарантировать отсутствие гонки с apply невозможно.
