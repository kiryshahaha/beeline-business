# Исходные файлы организатора (T11)

Отдельный профиль импорта дневных выгрузок организатора. Строгий обмен предметными
таблицами (`/api/v1/data/import`) не меняется: это другой, не обратимый формат.

## Какие файлы

На каждый участок два файла (CSV в Windows-1251 или UTF-8 с разделителем `;`/`,`/табуляция,
либо XLSX, где таблица может быть на любом листе):

| Вид (`kind`) | Файл | Что делает импорт |
| --- | --- | --- |
| `demand` | «<участок> Синтетические данные» | Каждая строка — визит и заявка на день; строка «Адрес офиса» под таблицей — офис и точка старта участка |
| `control` | «<участок> Контрольное распределение» | Как распределили у организатора: бригада и статус BK по тем же визитам. Сохраняется как базовая линия и replay, **не** как наши назначения |

Участок (`service_areas`, код `source-<транслит>`) берётся из имени файла до «Синтетические
данные»/«Контрольное распределение» или из параметра `dataset`. Столбцы узнаются по
смыслу (синонимы в `profile.py`): «Заявка», «Тип заявки BK», «Статус BK», «Тип заявки HD»,
«Начало», «Окончание», «Район», «Адрес», «Бригада», «Подключение», «Гигабитное
подключение». Время — Москва, «0:01–23:59» — окно на весь день. Незнакомые столбцы
сохраняются в исходной строке и перечисляются в отчёте.

## API (observer)

| Запрос | Назначение |
| --- | --- |
| `POST /api/v1/data/sources/import` | Файл `file`; `dry_run=true` по умолчанию (всё проверяется в транзакции и откатывается); `kind`, `dataset`, `geocode`; для контроля — смена и транспорт создаваемых исполнителей |
| `GET /api/v1/data/sources/imports`, `/imports/{id}` | Журнал и сохранённый отчёт импорта |
| `GET /api/v1/data/sources/addresses?service_area_id=&status=` | Адреса и статус координат: `unresolved`, `ambiguous` ждут проверки |
| `PUT /api/v1/data/sources/addresses/{id}` | Проверенные координаты вручную (`manual`) |
| `GET /api/v1/data/sources/areas/{id}/replay` | События контрольного дня |
| `GET /api/v1/data/sources/mapping` | Версия и таблицы соответствий |

Отчёт: `counts` (прочитано/создано/обновлено/без изменений/отклонено), `rejected` с листом,
строкой, столбцом, номером заявки и кодом (`unknown_source_type`, `invalid_time`,
`invalid_window`, `address_unparsed`, `missing_district`, `missing_external_id`,
`duplicate_row`, `ticket_in_work`, `unknown_source_status`, `no_matching_demand_row`),
`warnings`, `by_category`, `coordinates`, `office`; для контроля `baseline` и `replay`.

## Правила

- **Каждая строка — визит** (M21), включая «Информация» и «Мониторинг»: либо заявка, либо
  строка отчёта с причиной. Неизвестный тип не превращается в обычную заявку.
- **BK и HD — системы-источники** (C23/C24). Версия соответствий 1: тип BK выбирает норму
  «Нормативы.xlsx» — Подключение → `connection`, Дозаказ → `additional`, Локальная заявка →
  `repair`, Глобальная проблема → `emergency`. Тип HD хранится в происхождении.
- **Происхождение** каждой строки — `source_records`: участок, вид файла, лист, строка,
  внешний номер, BK/HD, статус BK, исходные ячейки, отпечаток строки, связанные заявка,
  исполнитель и адрес. Ключ — `(участок, вид, номер)`. Повтор номера с другим содержимым —
  ещё один визит той же заявки (`102#2`) с предупреждением; полностью одинаковая
  строка отклоняется.
- **Повторная загрузка**: та же строка — `unchanged`, изменённая — `updated`, пока заявка ждёт
  назначения; для заявки в работе — `ticket_in_work`, данные не меняются. Строки, которых нет
  в новой версии файла, не удаляются, а перечисляются в предупреждении.
- **Заявка**: вид работ, категория и приоритет — из справочника; длительность — работа +
  документы нормы; окно — «Начало»/«Окончание»; время поступления в файле нет, берётся начало
  окна. Адрес разбирается на город, улицу (тип приводится к одному написанию), дом, корпус и
  квартиру; район — столбец «Район». Неразобранный адрес отклоняет строку.
- **Бригада контрольного файла — один исполнитель** (T03). Идентичность — участок + подпись
  бригады: однофамильцы разных участков — разные люди (M08). Исполнитель получает участок,
  офис участка, смену и транспорт из параметров импорта (по умолчанию 09:00–22:00, car) и
  навыки кейса по видам работ, которые он выполнял: «Локальные работы», «Работы на
  подключение и дозаказы», «Аварийные работы». Пароль не известен — задаётся отдельно.
- **Утро и replay разделены** (M31): синтетика даёт весь утренний спрос, закрытые и
  отменённые в контроле визиты не исчезают. Replay: итоговые статусы (выполнена, отменена,
  просрочена) — с моментом конца окна (`time_basis=visit_window_end`, в файле нет времени
  события); остальные описывают момент выгрузки (`export_snapshot`, `at=null`).
- **Координаты**: в файлах их нет. `geocode=true` вызывает Geoapify до транзакции, только для
  адресов без результата. Уверенный ответ по дому — `geocoded`, координаты записываются;
  слабый — `ambiguous`, хранится кандидатом и в расчёт не идёт; пустой — `unresolved`.
  Планировщик не строит дорогу к адресу без координат (`missing_coordinates`).
- Если у видов работ нет требований планирования, отчёт предупреждает: заявки загружены, но
  не попадут в расчёт до настройки `/api/v1/work-types`.
- Лимиты: файл до 5 MiB, до 5000 строк, до 300 адресов на геокодирование за импорт.

## Файлы

| Файл | Ответственность |
| --- | --- |
| `profile.py` | Кодировка, разделитель, листы, синонимы заголовков, офис под таблицей, время |
| `classify.py` | Версия и таблицы соответствий BK → вид работ, категория → навык, статусы BK |
| `addresses.py` | Разбор адреса на уровни справочника |
| `geocoding.py` | Geoapify Geocoding и правила уверенности |
| `service.py` | Порядок импорта, спрос, контроль, replay, ручная проверка адреса |
| `repository.py`, `models.py`, `router.py`, `schemas.py` | SQL, таблицы, HTTP |
