# Модуль маршрутизации (Routing)

Модуль объединяет два направления работы с маршрутами:
1. **Расчёт маршрутов и матриц времени/расстояний** через внешний сервис Geoapify Routing API.
2. **Персистентное хранение и версионирование снимков маршрутов** в PostgreSQL, разграничение прав и экспорт в GeoJSON (RFC 7946).

---

## Структура модуля

| Файл | Назначение |
| --- | --- |
| `client.py` | HTTP-клиент `GeoapifyRoutingClient` к API Geoapify (маршруты и матрицы источников-целей) |
| `models.py` | Таблица `routes`, JSONB-снимок, уникальность `(worker_id, route_date, route_number)` |
| `schemas.py` | Контракты расчёта (`GeoPoint`, `RouteRequest`, `RouteResult`, `RouteMatrixResult`) и персистентного хранения (`RouteCreate`, `RouteRead`, `RouteGeoJSON`, `RouteStop`, `LineString`) |
| `service.py` | Бизнес-логика БД: проверка мест и заявок, сборка GeoJSON, блокировки работников и проверка прав |
| `router.py` | FastAPI роутер: расчёт маршрутов, пакетное сохранение, фильтрация, скачивание GeoJSON |

## 1. Расчёт маршрутов через Geoapify

Сервис вызывается наблюдателем (`observer`) и не раскрывает API-ключ клиенту.

### Эндпоинты:
- `POST /api/v1/routes` (или `POST /api/v1/routes/calculate`)
  
```json
{
  "origin": {"latitude": 55.7558, "longitude": 37.6173},
  "destination": {"latitude": 55.7903, "longitude": 37.5312},
  "mode": "drive"
}
```

Поддерживаемые режимы `mode`: `drive`, `transit`, `approximated_transit`, `walk`, `bicycle`, `scooter`, `motorcycle`.

Ответ:
```json
{
  "distance_meters": 11057.0,
  "duration_seconds": 968.0,
  "geometry": {
    "type": "MultiLineString",
    "coordinates": [[[37.6173, 55.7558], [37.5312, 55.7903]]]
  }
}
```

## 2. Сохранённые маршруты

Модуль хранит уже построенные маршруты. Он не запускает оптимизатор, не назначает исполнителей заявкам и не меняет расписание существующих заявок.

`id` — технический ключ. `route_number` — номер построения маршрута конкретного инженера на конкретный день: 1, 2, 3. Новая дата или другой инженер начинают с 1. `sequence` — номер точки внутри маршрута. Сохранённые записи неизменяемы; перепланирование создаёт следующую запись. Удаление работника каскадно удаляет его маршруты.

Для сохранения нужен `observer`. Читать свои маршруты может работник, маршруты текущих участников своей бригады — `foreman`, любые — `observer`. Чужой маршрут скрывается ответом 404. Список поддерживает `worker_id`, `route_date`, `limit` (1–100) и `offset`.

### Пример сохранения `POST /api/v1/routes`:

```json
{
  "worker_id": 9,
  "route_date": "2026-09-21",
  "stops": [
    {"location_id": 1, "arrival_at": "2026-09-21T09:00:00+03:00"},
    {"location_id": 2, "ticket_id": 20, "arrival_at": "2026-09-21T10:30:00+03:00"}
  ]
}
```

### Пакетное сохранение:
`POST /api/v1/routes/batch` принимает `{"routes":[...]}` до 100 маршрутов и сохраняет их одной транзакцией.

### Выгрузка GeoJSON:
`GET /api/v1/routes/{id}/geojson` возвращает самостоятельный файл `application/geo+json`.

## Использование планировщиком

Модуль planning вызывает AsyncGeoapifyRoutingClient для матриц и дорожных сегментов,
а save_routes_in_transaction — внутри общей транзакции apply. Публичное ручное
сохранение продолжает пользоваться save_routes, который сам открывает транзакцию.

Geoapify MultiLineString сохраняется вместе с path_properties: профиль, traffic,
индексы сегментов каждого перехода, расстояния и секунды. Проверяются порядок остановок,
покрытие сегментов и привязка крайних координат к остановкам (до 100 м по умолчанию).
Разрывы между линиями провайдера не превращаются в выдуманный прямой участок.
Старый LineString с точным совпадением концов остаётся допустим для ручных снимков.
