# Bruno: проверки API

Коллекция запускается **последовательно и целиком** на новой тестовой БД после
миграций и `seed_demo.py`. Первые папки проверяют существующие сценарии и сохраняют
токены/ID для последующих. Фиксированные имена и ожидания рассчитаны на один прогон
с чистого состояния; повторный запуск всей коллекции требует новой тестовой схемы/БД.

| Папки | Сценарии |
| --- | --- |
| 01, 05 | Liveness и readiness API, вход наблюдателя, исполнителей и бригадира |
| 02–04 | Фильтры и пагинация заявок, создание, ошибки и `401` без авторизации |
| 06–08 | Назначения, запрет смены статуса исполнителем, комментарии, уведомления |
| 09–11 | Офисы, бригады, оборудование и склад |
| 12-worker-transport | Четыре вида транспорта, сохранение профиля, ошибки и доступ |
| 13-routes | Номер по инженеру/дню, история, GeoJSON, скрытие чужого маршрута, валидация |
| 14-data-exchange | 21 таблица, обе выгрузки, dry run, XLSX-импорт, повтор через CSV, ошибки и роли |
| 15-work-types | Справочник видов работ: сумма норматива, чтение по ID, создание и изменение наблюдателем, `403`, `404`, `409`, `401` |
| 16-planning | Планирование маршрутов через решатель |
| 17-schedule | Таймлайн офиса на сутки, ночная смена, все офисы, `403` исполнителю, `404`, `422`, `401` |
| 18-analytics | Сводка заявок, загруженность бригад и лента последних действий: области observer/foreman, запрет worker и ошибки авторизации |
| 19-reports | Выгрузка заявок наблюдателем в CSV/XLSX, фильтры, формат по умолчанию, текст-формула в CSV, пустая выгрузка, `401`, `403` и `422`; отчёт по плану из 16-planning: XLSX, CSV-архив, `404`, `403` |
| 20-calendar | Ссылка на календарь исполнителя, скачивание .ics без JWT, статус, `403`, `404`, отзыв |
| 21-worker-line-status | Снятие инженера с линии, сохранение текущей заявки, запрет нового назначения, роли, `401`, `404`, возврат на линию |
| 22-execution | Создание заявки, назначение, сдвиг окна, путь, работа, задержка, завершение, безопасный повтор, переоткрытие, отмена, снимок дня и недоступность |
| 23-worker-history | Инженер применённого плана: смена роли и архив без передачи работы — `409`, удаление — `409` со связями истории, план показывает бригаду; новый исполнитель: архив, вход `403`, скрытие из списка, восстановление, удаление, `403`, `404` |
| 22-worker-equipment | Комплект по заявкам из 16-planning, выдача, повтор по ключу, «нечего выдавать», возврат позиции заявки, журнал, роли, `401` |
| fixtures | Небольшой полностью вымышленный пакет: 24 заявки, 4 работника; ошибочный CSV |

Из backend в отдельной тестовой БД:

```powershell
python -m alembic upgrade head
python seed_demo.py
python -m uvicorn app.main:app --port 8000
```

В другом терминале из `backend/bruno`:

```powershell
npx --yes @usebruno/cli@4.1.0 run -r --env Local --reporter-junit ../bruno-results.xml
```

Для другого порта добавьте `--env-var base_url=http://127.0.0.1:18000`.
`environments/Local.bru` и `collection.bru` содержат только опубликованные
демонстрационные учётные данные. Не заменяйте их реальными паролями.

Файлы загрузки задаются относительно корня коллекции: `@file(fixtures/dataset.zip)`.
У запроса Bruno режим `body: multipartForm`, а блок данных — `body:multipart-form`.
Обновление fixtures, из backend:

```powershell
python generate_synthetic.py --output bruno/fixtures --seed 906 --tickets 24 --workers 4 --days 1
```

CI поднимает PostgreSQL, выполняет миграции/seed, ждёт `/health`, запускает всю
коллекцию и сохраняет JUnit. Падение assertions/tests возвращает ненулевой код.

Папка 16-planning проверяет импорт набора на 24 заявки, preview, второй конкурирующий
preview, применение, повтор, конфликт устаревшего плана, чтение состояния и GeoJSON,
запрет для исполнителя и неизвестный ID. Требует работающего planner и включённого
PLANNING_ENABLED. Ошибки 503 не считаются успешным прохождением.

T01 в 16-planning: чтение `/planning/policy` наблюдателем, `401` без токена,
`403` работнику и `422` при попытке заменить политику через preview. Параметры
сверяются между `/policy`, preview и сохранённым планом, в том числе после
изменения норм работ. `case_contract.activation=contract_only` не выдаётся за
активную цель OR-Tools.

T10 в 16-planning: preview содержит `outcome`, `metrics` и `factors` каждого визита;
повторный расчёт уже назначенных заявок возвращает `201` с `outcome=empty`, причинами
`already_assigned` и `solver_status=null`, а его apply — `409 plan_has_no_assignments`.

Для полного воспроизводимого прогона из backend используйте run_planning_e2e.py.
Он сам поднимает тестовое окружение с реальным OR-Tools. При ручном запуске всей
коллекции нужен GEOAPIFY_API_KEY; обращения к настоящему Geoapify расходуют квоту.
