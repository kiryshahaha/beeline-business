## Результаты трёх задач

### CSV/XLSX

Контракт: [DATA_EXCHANGE.md](DATA_EXCHANGE.md), реализация:
[data_exchange](../backend/app/modules/data_exchange/README.md).

- Выгрузка всех строк 21 предметной таблицы одним согласованным снимком БД.
  CSV — ZIP с таблицами и manifest; XLSX — лист на таблицу и версия формата.
- Импорт пакета либо одиночного CSV. По умолчанию dry run; запись атомарная.
  Новые ID переназначаются вместе с FK, ссылками внутри GeoJSON и уведомлений.
- Проверены повторный и параллельный импорт, полный откат при ошибке,
  перенос между независимыми схемами с другим диапазоном ID.
- Контроль типов, диапазонов/точности, времени с поясом, версий, структуры,
  формул, размера, архивов, NULL/пустого текста/управляющих символов.
  Длинная XLSX-ячейка отклоняется с предложением CSV, без обрезки текста.
- Доступ только observer. Пароли и токены не экспортируются; импортированные
  пользователи получают неизвестные случайные пароли. История уведомлений
  импортируется без повторной внешней отправки.

Это перенос предметных данных с созданием записей, а не merge по имени и не
резервная копия секретов. Выгрузка содержит персональные поля пользователей,
поэтому требует роли observer. Произвольный формат сторонней CRM не угадывается.

### Маршруты

Контракт: [routes](../backend/app/modules/routes/README.md).

- Отдельная таблица `routes`, неизменяемые снимки GeoJSON FeatureCollection.
- `id` и `route_number` — разные значения. Номер начинается с 1 для каждой пары
  инженер/дата; повторное сохранение в этот день получает следующий номер.
  Проверены 12 параллельных сохранений без повторяющихся номеров.
- Точки содержат порядок, место, необязательную заявку, время прибытия с поясом.
  Поддерживаются ночь через полночь, один пункт, пакет из нескольких маршрутов.
- Создание observer; чтение worker только своих, foreman своей текущей бригады,
  observer всех. Чужая запись возвращает 404.
- Проверяются координаты, согласованность заявки/места, порядок времени,
  структура GeoJSON и соответствие концов предоставленной линии точкам.

Операция сохраняет уже рассчитанный план. Без готовой геометрии строится явно
помеченная линия между точками; это не дорожный маршрут и не расчёт времени пути.
API не меняет назначения заявок. Дата интерпретируется по московскому времени,
максимальная длительность одного маршрута — 24 часа.

### Транспорт

В `worker_profile.transport_type` доступны `car`, `walking`, `bicycle`,
`public_transport`. Существующие работники после миграции и старые запросы
создания без поля получают `walking`. PATCH без поля сохраняет текущее значение;
`null` и неизвестные значения отклоняются. Поле присутствует в выдаче пользователей,
`/users/me`, полном обмене и синтетических наборах.

Миграции [0009](../backend/migrations/versions/0009_worker_transport.py) и
[0010](../backend/migrations/versions/0010_routes_and_data_imports.py)
применены к новым схемам и заполненной схеме 0008. Проверен откат до 0008
с сохранением прежних полей работников; откат удаляет новые данные маршрутов,
как описано в README миграций.

## Найденные проблемы существующей системы

Приоритет P1 — существенный риск доступа/целостности; P2 — важная корректность
или ограничение. Приведённые ниже механизмы не менялись в рамках трёх задач.

### P1. Доступ к заявкам без авторизации — воспроизведено

[tickets/router.py](../backend/app/modules/tickets/router.py), строки 26–70:
GET использует необязательного пользователя, POST не требует пользователя.
В отдельной тестовой схеме GET без токена вернул 200, POST — 201 и создал заявку.
Аналогичное отсутствие зависимости видно у POST в
[locations/router.py](../backend/app/modules/locations/router.py), строка 17.

Последствие: при доступности API посторонний может читать заявки и добавлять данные.
В docstring GET явно сохранена совместимость, поэтому изменение требует отдельного
решения об авторизации старых клиентов. Новые маршруты и обмен требуют токен/роль.

### P1. Повторное закрытие повторно списывает оборудование — воспроизведено

[tickets/service.py](../backend/app/modules/tickets/service.py), `update_ticket_status`
(строка 127), и [appliances/repository.py](../backend/app/modules/appliances/repository.py),
`consume_ticket_appliances_on_completed` (строка 253).

Для заявки с двумя единицами расходника последовательность
`planned → completed → planned → completed` дала остатки `72 → 70 → 70 → 68`.
Все три HTTP-запроса вернули 200. Повтор одинакового `completed` защищён,
но переоткрытие снимает эту защиту. Требуется согласовать допустимые переходы
и учёт однократного расхода/возврата, иначе остаток расходится с реальностью.

### P1. Параллельная ротация refresh-токена — воспроизведено

[auth/repository.py](../backend/app/modules/auth/repository.py),
`find_active_refresh_token` (21) и `revoke_refresh_token` (38);
[auth/service.py](../backend/app/modules/auth/service.py), `refresh_access_token`.

Две независимые транзакции прочитали один активный токен до отзыва. В тестовой
проверке чтения синхронизированы барьером; обе ротации завершились успешно,
остались два активных заменяющих refresh-токена. UPDATE отзыва не проверяет число
затронутых строк, а SELECT не блокирует запись. Для исправления нужна атомарная
проверка/ротация; реальные токены в отчёте не сохраняются.

### P2. Проверка резерва при ручном изменении остатка — статический риск

[appliances/service.py](../backend/app/modules/appliances/service.py),
`set_office_stock`: сумма резервов читается до изменения/блокировки остатка.
Другой запрос может зарезервировать оборудование между чтением и записью.
Возможен итоговый остаток ниже актуального резерва. Конкурентное воспроизведение
именно этого сценария не проводилось; вывод основан на порядке операций.
Новый импорт блокирует складские строки до проверки своего резерва.

### P2. Planner принимает некорректные индексы/длины — проверено на DTO

[solver/schemas.py](../planner/app/modules/solver/schemas.py),
`validate_dimensions` (строка 49): нет полной проверки `starts`/`ends`,
длины `penalties`, допустимости длительностей, окон и параметров поиска.
`SolveRequest.model_validate` принял `starts=[999]` для матрицы 2×2 и `penalties=[]`.
Передача такого ввода в native OR-Tools в этой проверке не выполнялась.
Возможные исключения или аварийное завершение solver — риск, а не заявленный
результат локального воспроизведения. Нужна валидация до вызова библиотеки.

### P2. Статус OPTIMAL не подтверждает оптимальность — подтверждено кодом

[solver/service.py](../planner/app/modules/solver/service.py), строка 102:
для любого найденного assignment жёстко выставляется `OPTIMAL`, хотя поиск
эвристический и ограничен временем. Клиент не может отличить найденное допустимое
решение от доказанного оптимума. Документация уточнена; код solver не изменялся.

### Продуктовые и эксплуатационные ограничения

- Frontend пока шаблон Next.js. Нет экрана диспетчера, карты или формы импорта.
  Новые операции доступны через API/Swagger/Bruno.
- Backend и planner не соединены автоматическим адаптером. Нет полного потока
  «новая заявка → пересчёт → сохранение → отображение». Транспорт хранится, но
  автоматический выбор матрицы/допусков по нему ещё не реализован.
- В модели заявки отсутствуют отдельные поля приоритета и требований к транспорту.
  Полный кейс автоматического перепланирования/SLA требует дополнительных задач.
- Docker Compose и локальные примеры содержат демонстрационные значения секретов
  и публикуют порты. Для внешнего развёртывания требуется собственная конфигурация;
  развёртывание не выполнялось.
- Экспорт собирается в памяти. Проверен набор 46 496 строк; это не замер
  предельной производительности. Для существенно больших объёмов нужен потоковый
  вариант. XLSX ограничен длиной ячейки; CSV сохраняет длинный текст/GeoJSON.

## Ревью итоговых изменений

Проверены границы доступа, защита credential-полей, атомарность, FK и ссылки в JSON,
совместимость старых запросов, блокировки параллельных сохранений/импортов,
точность CSV/XLSX и миграции. При ревью устранены ошибки новых частей: потеря
пустой строки XLSX, недопустимые XML-символы, неверный номер строки после пустых
строк, необработанная ошибка данных PostgreSQL, тихое округление координат,
перенос actor_id уведомления и проверка null-типа GeoJSON на уровне БД.
Соответствующие проверки добавлены и прошли.

Для завершения проверки всего окружения после восстановления доступа к пакетам
нужно установить полные requirements backend/planner и повторить команды из
корневого README либо запустить подготовленный workflow в GitHub.
