# CSV/XLSX: единый обмен предметными данными

## Доступ и HTTP

Все операции доступны только авторизованному `observer`. Без токена — 401,
с другой ролью — 403.

| Метод | Путь | Результат |
| --- | --- | --- |
| GET | `/api/v1/data/schema` | Таблицы, поля, типы, nullable, версия и исключения |
| GET | `/api/v1/data/export?format=xlsx` | Один XLSX со всеми 38 таблицами |
| GET | `/api/v1/data/export?format=csv` | ZIP с 38 CSV и `manifest.json` |
| POST | `/api/v1/data/import?dry_run=true` | Проверка файла и ограничений БД без записи |
| POST | `/api/v1/data/import?dry_run=false` | Атомарное добавление пакета |
| POST | `/api/v1/data/import?entity=cities&dry_run=false` | Импорт одиночного CSV указанной таблицы |

Файл отправляется в multipart-поле `file`. Расширение: `.csv`, `.zip` или `.xlsx`.
У `dry_run` значение по умолчанию **true**. Для XLSX и ZIP параметр `entity` не задаётся.

Пример из PowerShell (`$token` — access token диспетчера):

```powershell
curl.exe -H "Authorization: Bearer $token" `
  'http://127.0.0.1:8000/api/v1/data/export?format=xlsx' -o all-data.xlsx
curl.exe -H "Authorization: Bearer $token" -F 'file=@all-data.xlsx' `
  'http://127.0.0.1:8000/api/v1/data/import?dry_run=true'
```

Импорт экспортированного пакета в **другую** БД переносит данные. Импорт в ту же БД
с уже существующими уникальными именами отклоняется: существующие записи не
перезаписываются и не сливаются автоматически.

## Таблицы

Адреса: `cities`, `districts`, `streets`, `buildings`, `entrances`, `locations`.
Сотрудники: `users`, `workers`, `worker_skills`, `worker_skill_assignments`.
Организация: `offices`, `brigades`, `brigade_members`.
Работа: `tickets`, `ticket_assignments`, `ticket_comments`.
Оборудование: `appliances`, `appliance_stocks`, `ticket_appliances`.
История: `notification_events`, `routes`.

`users.password_hash`, `refresh_tokens`, `calendar_tokens`, `push_subscriptions`
и `data_imports` исключены. Из `day_plan_revisions` исключён `plan_id`: он ссылается
на preview, а `planning_plans` не переносятся, поэтому UUID указывал бы в пустоту.
`ticket_assignment_events` тоже не переносится: это журнал действий именно этой базы,
его пишет её триггер, и перенесённые заявки начинают историю назначений заново.
Импортированные пользователи получают случайный неизвестный пароль;
диспетчер задаёт пароль через существующий PATCH пользователя. Для тестовых схем
`seed_synthetic.py` отдельно устанавливает документированный тестовый пароль.

Справочник work_types и таблицы work_type_planning_rules, work_type_required_skills,
work_type_required_appliances включены. Вычисляемое norm_minutes проверяется по сумме,
но не вставляется явно. Если одноимённый вид работ уже существует с теми же нормативами,
используется его ID; отличающиеся нормативы отклоняют весь пакет. Другие сущности
с уникальными конфликтами не сливаются.

Ревизии плана дня уникальны по участку и дате: у пары есть ровно одна текущая версия.
Поэтому импорт в базу, где этот день уже известен, не вставляет свою нумерацию поверх
чужой, а продолжает цепочку: номера сдвигаются за существующий максимум, а прежняя
текущая ревизия закрывается как заменённая.

Служебные planning_plans/planning_plan_routes
не переносятся: их снимки привязаны к исходной базе. Журнал и остатки оборудования на руках
(office_kit_reserves, worker_appliances, appliance_operations, appliance_movements,
ticket_appliance_states) пока тоже не переносятся — это отдельная задача T11. Сохранённые routes переносятся,
включая MultiLineString и метаданные дорожных переходов.


Импорт событий уведомлений сохраняет историю, но не отправляет её заново:
отсутствующие метки доставки заполняются временем импорта. Вложенные `ticket_id`
и `worker_id` в данных события переназначаются вместе с соответствующими записями.
Это осознанное отличие от восстановления резервной копии.

## Файловый формат 2 (импорт также принимает 1)

У XLSX каждый предметный лист назван по таблице. Первая строка — имена полей.
Лист `_meta` содержит ровно одну строку: `format_version` и строковое значение `1`.
CSV-пакет содержит плоские файлы `<table>.csv` и
`manifest.json` с `{"format_version":"3"}` (пакеты форматов 1 и 2 тоже читаются). Подпапки и неизвестные файлы запрещены.
Можно передавать подмножество таблиц. Пустые таблицы содержат строку заголовков.

CSV: UTF-8 с необязательным BOM; разделитель запятая, точка с запятой или табуляция.
Экспорт использует запятую и BOM. Значения с разделителями, кавычками и переносами
экранируются по правилам CSV. Числа используют точку, не локальную десятичную запятую.
Координаты соответствуют точности БД: максимум 6 знаков после запятой;
избыточная точность отклоняется, чтобы импорт не округлял данные незаметно.

| Тип | Представление |
| --- | --- |
| NULL | `\N`; в XLSX также допускается пустая ячейка для nullable-поля |
| Пустой текст | `\E` (пустая строка CSV также допустима для текстового поля) |
| Дата | `2026-09-21` |
| Момент времени | `2026-09-21T09:30:00+03:00`; часовой пояс обязателен |
| Время смены | `09:00:00` без часового пояса |
| Boolean | `true`/`false` (также принимаются `1`/`0`) |
| JSONB | JSON-объект в одной текстовой ячейке, включая GeoJSON |
| ID | Положительное целое число int32, исходный ключ внутри пакета |

Экспорт экранирует потенциальные формулы префиксом `'`, а также литералы,
начинающиеся с `'` или `\`. Импорт снимает ровно этот префикс. Поэтому настоящий
текст `\N` отличается от NULL. `\E` сохраняет пустой текст, а `\T` с JSON-строкой
сохраняет управляющие символы, недопустимые непосредственно в XML XLSX.
Формулы и значения ошибок Excel отклоняются;
макросы и `.xls` не поддерживаются. XLSX выгружается строковыми ячейками, чтобы
Excel не менял ID, даты и ведущие нули. Если GeoJSON длиннее 32 767 символов
(лимит ячейки считается в единицах UTF-16: эмодзи — два), используйте CSV:
экспорт XLSX вернёт понятную ошибку вместо обрезки.

Точные столбцы и типы можно получить через `/api/v1/data/schema` или посмотреть
в готовом наборе. Формат отражает действующую модель проекта; произвольные колонки
из сторонней CRM требуют явного преобразования, не угадываются.

## Связи, повторный запуск и ошибки

База генерирует новые ID. Все внешние ключи внутри переданных таблиц переназначаются,
включая составные адресные ключи и ссылки внутри GeoJSON. Если родительская таблица
присутствует в пакете, ссылка должна вести в неё; отсутствующий исходный ID — ошибка.
Если родительская таблица не передана, числовая ссылка означает уже существующий
ID целевой БД. Новые работники требуют подходящей роли пользователя, а новые
пользователи с ролью worker — профиля в том же пакете.

Весь пакет проверяется и добавляется одной транзакцией. Уникальные имена, внешние
ключи, ограничения БД, структура маршрутов и доступный складской остаток проверяются
до фиксации. Ошибка возвращает 422 с `detail.message`, `table`, `row`, `column`,
когда они известны. Номер строки включает заголовок: первая запись — строка 2.
SQL и пароли в ошибках не возвращаются. Для бизнес-проверок всего пакета строка
может отсутствовать.

Ответ содержит `fingerprint`, `counts`, `id_map`, `dry_run`, `duplicate`. Успешно
записанный пакет с теми же нормализованными данными, включая порядок строк,
повторно не добавляется — возвращается исходная квитанция с `duplicate=true`.
CSV и XLSX, созданные из одинаковых данных, дают одинаковый fingerprint.
Параллельные загрузки одного пакета сериализуются блокировкой PostgreSQL.
Dry run не создаёт квитанцию и не сохраняет строки; последовательности ID могут
продвинуться, что нормально для PostgreSQL и не создаёт предметных записей.

Маршрут импортируется как исторический снимок. Координаты могут отличаться от
сегодняшнего адресного справочника. Номер, инженер и дата внутри GeoJSON должны
совпадать с колонками маршрута, а ссылки на места и заявки должны существовать.

Лимиты импорта: 20 MiB файла, 100 MiB распакованного архива, 500 ZIP-элементов,
100 000 строк на таблицу, 250 000 строк суммарно, 1 000 000 символов в CSV-ячейке.
Большие выгрузки не обрезаются пагинацией API. Сейчас они собираются в памяти;
для объёмов значительно больше опубликованного набора потребуется потоковый экспорт.
