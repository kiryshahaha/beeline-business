# Эксплуатация backend

Что поддерживается в текущем развёртывании, что система пишет в журнал, как она ведёт
себя при конкуренции за общий замок, что и когда удаляет и как сделать резервную копию.
Запуск и переменные окружения — в [RUNTIME.md](RUNTIME.md).

## Режим доставки обновлений

**Поддерживается один процесс backend** (так запускает `Dockerfile`: `uvicorn` без
`--workers`). Живые события WebSocket доставляет только он; общего канала между
процессами нет, брокер сообщений не используется.

- Событие остаётся в `notification_events` — это история получателя. Отметка
  `websocket_delivered_at` ставится, только если событие получил хотя бы один открытый
  сокет. Если получатель не был подключён, ставится `websocket_missed_at`, и событие
  дойдёт до него из истории.
- Клиент запоминает `id` последнего полученного события и при переподключении передаёт
  его в первом сообщении: `{"type": "authenticate", "token": "…", "last_event_id": 42}`.
  Сервер присылает пропущенное по возрастанию `id` (до 200 событий) в том же формате,
  что и живые. Если пропущено больше, приходит
  `{"type": "replay_truncated", "next_after_id": N}`, а остальное клиент забирает
  `GET /api/v1/notifications?after_id=N` без пропусков. Одно событие на одном сокете
  не отправляется дважды, даже если оно попало и в догонку, и в живую доставку.
- Роль доставляющего процесса — session advisory lock PostgreSQL на отдельном
  соединении. Если по ошибке запущено несколько процессов, доставляет тот, у кого замок;
  остальные закрывают новые сокеты с кодом `1013` («попробуйте позже»), и клиент
  переподключается и догоняет историю. Так локальная память одного процесса не выдаётся
  за общую доставку. Если соединение владельца обрывается, PostgreSQL снимает замок, и
  роль может перейти к другому процессу; сокеты процесса, потерявшего роль, закрываются
  с кодом `1012`.
- Несколько процессов с живой доставкой в каждом **не поддерживаются**. Для этого нужен
  общий канал (например, `LISTEN/NOTIFY` PostgreSQL) и отдельная проверка в этом режиме.

## Журнал операций

Логгер `beeline.ops` пишет в stdout по одной JSON-строке на операцию. Уровень —
`OPERATION_LOG_LEVEL` (по умолчанию `INFO`).

```json
{"ts":"2030-01-15T09:00:01+00:00","level":"info","event":"planning.apply","request_id":"3f2a…",
 "plan_id":"…","day_revision":3,"routes":4,"assigned_tickets":24,"outcome":"ok",
 "duration_ms":41.7,"stages":{"lock_wait":{"calls":1,"duration_ms":0.4},
 "snapshot":{"calls":2,"duration_ms":18.9}}}
```

| Событие | Когда | Поля |
| --- | --- | --- |
| `planning.preview` | Каждый расчёт | `plan_id`, `route_date`, `service_area_id`, запрошенные и назначенные заявки, `solver_status`, `plan_outcome`; этапы `snapshot`, `matrix_build`, `solver`, `route_fetch` (геометрия), `diagnostics` |
| `planning.apply` | Каждое применение | `plan_id`, `day_revision`, `routes`, `already_applied`; этапы `lock_wait`, `snapshot` |
| `planning.lock_timeout`, `planning.lock_wait_slow` | Замок не выдан вовремя или ждали дольше секунды | `waited_ms`, `timeout_ms` |
| `notifications.delivery_role` | Процесс получил, не получил или потерял роль доставки | `role`: `primary`, `secondary`, `lost` |
| `maintenance.cleanup` | Каждый проход очистки | `deleted` по правилам, `skipped` |

`outcome` — `ok` или код ошибки (`plan_stale`, `planning_lock_timeout`…); неуспешная
операция пишется с уровнем `warning`. `request_id` совпадает с заголовком ответа
`X-Request-ID`: сервер принимает корректный идентификатор клиента или создаёт свой.

В журнал не попадают токены, адреса, тексты заявок и комментариев, ФИО. Фильтр
двойной: ключи вроде `token`, `address`, `title`, `comment`, `name` отбрасываются при
любом значении, а строка проходит только как идентификатор или код (строчные буквы,
цифры, `_.:-`) или короткое значение перечисления прописными (`FEASIBLE`). Токены —
base64 со смешанным регистром и никогда не проходят. Прежний текстовый журнал отказов
расчёта (`planning_failed …`) и журнал доступа uvicorn с маскировкой токенов в URL
остались как были.

## Общий планировочный замок

Один транзакционный advisory lock (`app/core/planning_guard.py`) сериализует проверку
снимка при применении плана, изменение назначений и все складские операции: они
затрагивают пересекающиеся строки (заявки, исполнители, остатки офиса), и более мелкий
ключ разделил бы их только ценой новых гонок. Поэтому замок остаётся общим, а
ограничено ожидание:

- ожидание — не больше `PLANNING_LOCK_TIMEOUT_SECONDS` (по умолчанию 5 с); тот же предел
  действует для блокировок строк до конца транзакции;
- при превышении запрос получает `503 {"code": "planning_lock_timeout", "retryable": true}`
  с `Retry-After: 2`, транзакция откатывается целиком, ничего не записано;
- каждое ожидание попадает в этап `lock_wait` операции, ожидание дольше секунды и отказ —
  отдельными записями.

Сетевых вызовов под замком нет: применение записывает заранее рассчитанный результат.
Измерения — в разделе [результаты измерений](#результаты-измерений).

## Хранение и очистка

| Данные | Срок |
| --- | --- |
| Непримененные предпросмотры (`planning_plans`, кроме `applied`) | Удаляются через `PREVIEW_RETENTION_HOURS` (24 ч) после истечения TTL |
| Доставленные уведомления (`notification_events`, оба канала завершены) | Удаляются через `NOTIFICATION_RETENTION_DAYS` (90 дней); `0` — хранить всегда |
| Применённые планы со снимками, маршруты, ревизии плана дня, `work_events`, история назначений, состояния дня, квитанции импорта | Хранятся всегда: это история, объясняющая день |

Проход запускается внутри backend раз в `RETENTION_INTERVAL_MINUTES` (60; `0` — выключено),
первый — через интервал после старта. Одновременно работает только один проход (свой
advisory lock), удаление идёт пачками по 500 строк, каждая пачка — короткая транзакция под
общим планировочным замком, поэтому одновременное применение видит предпросмотр целиком
или получает `plan_not_found`. Вручную:

```bash
docker compose exec backend python cleanup.py          # сколько будет удалено
docker compose exec backend python cleanup.py --apply  # удалить
```

## Резервное копирование и восстановление

Резервная копия — это дамп PostgreSQL, а не выгрузка CSV/XLSX. Обмен файлами переносит
предметные данные между базами и сознательно не содержит паролей, токенов, предпросмотров,
журнала назначений и служебных таблиц (см. [DATA_EXCHANGE.md](DATA_EXCHANGE.md)), поэтому
восстановить из него рабочую систему нельзя.

Копия (версия `pg_dump` в контейнере совпадает с сервером):

```bash
docker compose exec -T db pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc > beeline-$(date +%F).dump
```

Восстановление в пустую базу:

```bash
docker compose stop backend
docker compose exec -T db dropdb -U "$POSTGRES_USER" --if-exists "$POSTGRES_DB"
docker compose exec -T db createdb -U "$POSTGRES_USER" "$POSTGRES_DB"
docker compose exec -T db pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner --exit-on-error < beeline-YYYY-MM-DD.dump
docker compose start backend   # entrypoint выполнит alembic upgrade head, если копия старее кода
curl -fsS http://localhost:8000/ready
```

Проверка процедуры (2026-09-26, PostgreSQL 17): синтетический набор `seed_synthetic.py
--seed 42` (47 таблиц, 6904 строки, из них 1500 заявок и 896 маршрутов) выгружен
`pg_dump -Fc` и восстановлен `pg_restore` в новую базу; число строк совпало во всех 47
таблицах, версия Alembic сохранилась. Проверка ручная, в CI не входит: версия `pg_dump`
раннера GitHub не совпадает с сервером 17.

## Результаты измерений

Источник — журнал `beeline.ops` локального прогона `run_planning_e2e.py` (реальный
planner, PostgreSQL 17, фикстура Geoapify) 2026-09-26. Выборка маленькая: это порядок
величин для выбора пределов, а не нагрузочный тест.

| Операция, этап | Успешных | Медиана, мс | Максимум, мс |
| --- | --- | --- | --- |
| `planning.preview` целиком | 4 | 1362 | 1403 |
| — `snapshot` (чтение входных данных) | 4 | 46 | 70 |
| — `matrix_build` | 3 | 27 | 50 |
| — `solver` (лимит поиска решателя) | 3 | 1068 | 1079 |
| — `route_fetch` (геометрия) | 3 | 100 | 105 |
| — `diagnostics` | 3 | 2 | 8 |
| `planning.apply` целиком (замок удерживается всё это время) | 2 | 333 | 655 |
| — `lock_wait` | 2 | 3 | 7 |

Самое долгое применение (24 заявки, 4 маршрута) держало замок около 0,66 с, а ожидание
замка без конкуренции — единицы миллисекунд. Расчёт (preview) замок не берёт: решатель и
провайдер работают вне транзакции. Поэтому предел ожидания 5 с покрывает несколько
последовательных применений подряд и при этом не оставляет запрос висеть; дольше ждать
имеет смысл только при зависшей транзакции, и тогда клиент получает `503` и повторяет.
Сужать ключ замка по этим измерениям не нужно: удержание короткое, а разделение ключа
сломало бы общую защиту склада и назначений.
