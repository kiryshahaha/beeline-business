# План: графики смен и аварийные заявки

## Цель

Согласовать работу импорта, хранения графиков инженеров и планировщика с уточнениями экспертов:

- для планирования рассматривается один отдельно взятый рабочий день;
- в рамках этого дневного scope обозначения 2/2 и 5/2 задают продолжительность сменного интервала: 12 и 8 часов соответственно;
- в Москве чаще используется 12-часовая смена; контрольные данные показывают примерный интервал с 10:00 до 22:00;
- авария определяется полем `request_type_hd`;
- если во входном файле нет времени поступления аварии, допустимо считать её известной утром при первоначальном планировании либо моделировать её как событие в течение дня;
- при событийной модели норматив реакции 1–2 часа отсчитывается от времени поступления.

План относится к существующей архитектуре backend + единственный planner `POST /api/v1/solve`. Новую версию planner создавать не требуется. Он описывает предполагаемые работы, а не уже реализованное поведение.

## Текущее состояние проекта

План составлен по текущему `main`, HEAD `03db977`.

- В профиле инженера хранятся только `workshift_start` и `workshift_end`. График рассчитывает один день; недельный цикл, производственный календарь и определение выходных не входят в scope.
- Обычные схемы профиля используют значения по умолчанию `09:00–18:00`, а импорт контрольных данных — `09:00–22:00`. Это разные значения, и их нужно согласовать.
- Импорт распознаёт колонку HD как `hd_type` и сохраняет её в происхождении строки. Категория `emergency` сейчас определяется по типу BK «Глобальная проблема».
- В исходных файлах нет времени поступления; импорт записывает в `received_at` начало окна. Для окна `00:01–23:59` это не является достоверным временем поступления.
- При создании аварийной заявки сервер по умолчанию задаёт срок `received_at + 24 часа`. Это срок решения, тогда как новый ответ экспертов описывает норматив реакции 1–2 часа.
- В проекте уже есть preview/apply планирования, журналы событий и API перепланирования остатка дня с ревизиями. Эти механизмы нужно расширить и согласовать с новыми полями.

Основные места текущей реализации: [профиль инженера](backend/app/modules/users/models.py), [профиль импорта](backend/app/modules/source_import/profile.py), [классификация источников](backend/app/modules/source_import/classify.py), [создание заявок](backend/app/modules/tickets/service.py), [проверка смен и заявок](backend/app/modules/planning/eligibility.py), [перепланирование дня](backend/app/modules/planning/router.py).

## Правила, которые нужно зафиксировать до реализации

1. Составить явную таблицу значений `request_type_hd`, которые означают аварию. Не выводить признак аварии из окна, названия заявки или типа BK. Неизвестное значение должно быть показано в отчёте импорта и не должно молча превращаться в обычную заявку.
2. Использовать тип BK для определения вида работ и норматива обслуживания; использовать `request_type_hd` для аварийной классификации. Не смешивать категорию планирования, вид работ, норматив и исходное значение источника.
3. Задать только однодневный сменный интервал. В выбранной настройке режима 2/2 используется длительность 12 часов, режима 5/2 — 8 часов; опорную дату цикла и дни недели не вычислять.
4. Считать `10:00–22:00` примером 12-часовой смены из контрольных данных. Не применять его автоматически ко всем существующим профилям; время начала задаётся настройкой/данными, а время окончания согласуется с длительностью выбранного режима.
5. Установить значение нормы реакции в диапазоне 60–120 минут. Пока точное значение не утверждено, держать его настраиваемым и проверять оба предела; 120 минут можно использовать только как явно обозначенное допущение базового сценария.
6. Определить, что именно означает соблюдение реакции: прибытие инженера на адрес (`arrival_at`) или начало обслуживания (`service_start_at`). Эти времена различаются и не должны подменять друг друга.
7. Сохранить отдельный срок решения за 24 часа, если он остаётся частью требований. Норматив реакции 1–2 часа и срок решения нельзя хранить как один неоднозначный SLA.
8. Для контрольных файлов выбрать допущение «аварии известны при первом утреннем планировании» либо потребовать время события. Рекомендуемый вариант для файлов без времени — утренний план; динамическое поступление дополнительно покрыть отдельным сценарием.

## Итоговые критерии приёмки

- Для выбранного дня режим 2/2 задаёт 12-часовой интервал, а режим 5/2 — 8-часовой; система не рассчитывает дни недели или выходные.
- `10:00–22:00` применяется как явно заданный контрольный пример 12-часовой смены, а не как скрытая универсальная настройка.
- Аварийность определяется по `request_type_hd`; BK продолжает задавать вид работ и норму.
- Отсутствующее время поступления не заменяется `00:01` из окна на весь день без явного допущения.
- Реакция считается от поступления аварии по утверждённой временной метрике; срок решения заявки остаётся отдельным правилом.
- Невыполнимый SLA явно виден в ответе и объяснении планировщика.
- Поступление аварии в течение дня может быть безопасно просмотрено и применено через существующий replan с новой ревизией.
- CSV/XLSX, API профилей, расписание, планировщик и история маршрутов согласованы между собой.
- Локальные обязательные проверки и GitHub Actions реально проходят на чистой базе и с настоящим solver.

## Открытые решения

До полной реализации нужно подтвердить или выбрать:

1. Точные значения поля `request_type_hd`, означающие аварию.
2. Целевую границу реакции — 60 или 120 минут — либо правило выбора внутри диапазона.
3. Реакция измеряется по прибытии на адрес или по началу обслуживания.
4. Если SLA реакции невозможно соблюсти, разрешено ли назначить аварии поздний визит с явным нарушением или такой визит должен считаться недопустимым.
5. Фактическое время начала для конкретных работников/контрольных данных и допустимость исключений из стандартной длительности 12/8 часов.
6. Для исходных файлов без времени поступления используется режим «известно к началу первоначального планирования»; для динамического режима нужны точные времена событий.
