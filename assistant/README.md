# Ассистент (чат для адаптации сотрудников)

Отдельный stateless-сервис на FastAPI. Отвечает исполнителям, бригадирам и диспетчерам
на вопросы о смене и заявках, о работе в системе и о типовых работах. В БД сервис не
ходит: данные о пользователе передаёт основной бэкенд, правила берутся из базы знаний
в Markdown, формулирует ответы малая модель в Ollama.

## Как это работает

1. Бэкенд проверяет JWT, определяет роль и собирает контекст: «Мой день» исполнителя
   (`GET /api/v1/me/day`), открытую заявку с комментариями, оборудованием и историей
   изменений (`GET /api/v1/tickets/{id}/changes`).
2. Бэкенд вызывает `POST /api/v1/chat` этого сервиса.
3. **Вопросы о данных** — смена, сколько заявок, текущая и следующая заявка, время,
   адрес, статус, почему перенесли или сняли, что взять, комментарии — распознаются
   по шаблонам (`app/modules/chat/facts.py`), и ответ собирается прямо из контекста.
   Модель в этом не участвует, поэтому время, числа и причины всегда точные.
4. **Остальные вопросы** — «как сделать», правила, советы по работам — идут в модель:
   сервис ищет разделы базы знаний, доступные роли (BM25 со стеммингом русского языка,
   разделы по категории открытой заявки выше), и передаёт в Ollama правила роли,
   найденные разделы, тот же контекст и вопрос (`/api/chat`, без режима рассуждений).
   Если вопрос о данных не распознан, модель тоже видит контекст и пробует ответить.

Авторизации в самом сервисе нет: наружу его не публикуем, вызывает только бэкенд.

## API

`POST /api/v1/chat`

```json
{
  "role": "worker",
  "message": "Почему мою заявку перенесли?",
  "history": [
    {"role": "user", "content": "Привет"},
    {"role": "assistant", "content": "Здравствуйте! Чем помочь?"}
  ],
  "context": {
    "day": {"...": "ответ GET /api/v1/me/day"},
    "tomorrow_shift": {"is_working_day": false},
    "ticket": {"...": "TicketRead", "comments": [], "appliances": [], "changes": []}
  }
}
```

- `role` — `worker`, `foreman` или `observer`, берётся из токена на бэкенде.
- `history` — до 10 последних сообщений; сервис историю не хранит.
- `context` и все его поля необязательны. Объекты передаются как есть из ответов
  бэкенда: лишние поля сервис игнорирует. Пример полного контекста —
  [`eval/contexts.yaml`](eval/contexts.yaml), схема — в Swagger `http://127.0.0.1:8002/docs`.
- Время показывается по Москве, даты нужно передавать с часовым поясом.

Ответ:

```json
{
  "answer": "Заявку №104 «Заменить маршрутизатор» перенесли с 11:00 на завтра в 15:00 (изменено в 08:40): поступила аварийная заявка №120, маршрут пересчитан.",
  "source_type": "facts",
  "sources": [{"title": "Данные системы", "section": "История заявки №104"}],
  "model": null,
  "intent": "why_changed"
}
```

`source_type`: `facts` — ответ собран из данных системы (мгновенно, без модели);
`knowledge` — модель ответила по базе знаний; `model` — модель ответила по контексту без
справки. `503` — Ollama недоступна или модель не загружена (ответы из данных при этом
работают).

## База знаний

Формат файлов и правила — в [`knowledge/README.md`](knowledge/README.md). Памятки по
работам привязаны к категориям заявок (`emergency`, `connection`, `repair`,
`additional`); перезапуск сервиса подхватывает изменения.

## Запуск

В Docker вместе со всеми сервисами (Ollama и скачивание модели поднимутся сами):

```bash
docker compose up --build assistant
```

На машине с видеокартой NVIDIA:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up --build
```

Локально (Ollama должна слушать `http://localhost:11434`):

```bash
cd assistant
python -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.lock
.venv/bin/uvicorn app.main:app --reload --port 8002
```

Переменные: `OLLAMA_URL`, `ASSISTANT_MODEL`, `LLM_TEMPERATURE`, `LLM_NUM_CTX`,
`LLM_MAX_TOKENS`, `LLM_NUM_THREAD`, `RETRIEVAL_TOP_K` (см. `app/core/config.py`).

## Проверки

```bash
.venv/bin/python -m ruff check . && .venv/bin/python -m ruff format --check .
.venv/bin/python -m unittest discover -s tests -t .
```

`requirements.lock` фиксирует точные версии и хеши пакетов для Python 3.12.13; Docker
и GitHub Actions ставят тот же набор.

## Проверка качества

- `eval/intents.yaml` + `python -m eval.run_intents` — распознавание вопросов о данных
  на наборах формулировок `dev` (по нему настраиваются шаблоны) и `test` (не
  используется для настройки). Модель не нужна.
- `eval/questions.yaml` + `eval/contexts.yaml` — вопросы по ролям с ожидаемыми фактами.

```bash
.venv/bin/python -m eval.run_bench --facts-only
.venv/bin/python -m eval.run_bench --models qwen3.5:0.8b qwen3.5:2b
```

Отчёт с метриками и всеми ответами пишется в `eval/results/<время>/report.md`.
Автоматический балл — грубая проверка по ключевым словам; ответы модели нужно читать.
Итоги сравнений — в [`eval/RESULTS.md`](eval/RESULTS.md).

## Дообученная модель

`finetune/` — дообучение Qwen3.5-2B под сервис на Mac (MLX, LoRA): данные, обучение,
проверка и сборка GGUF. Готовую модель можно подключить без изменения кода — положить
GGUF в `model/model.gguf` и указать `ASSISTANT_MODEL=qwen3.5-beeline:2b`
(см. [`model/README.md`](model/README.md)). Без файла используется стандартная `qwen3.5:2b`.
